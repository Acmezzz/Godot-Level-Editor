# 通用 2D 关卡编辑器全面审查

审查日期：2026-11-25。基线：`d110a3d`，审查开始时 `src/` 下没有未提交的脚本改动。产品代码范围限于 `src/`：113 个 GDScript、1 个入口场景，脚本约 3.6 万行。契约以 [EDITOR_FEATURES](../EDITOR_FEATURES.md) 和 [GAME_SIDE_STANDARD](../GAME_SIDE_STANDARD.md) 为对照；未借用归档结论，未审查游戏运行时代码、插件或仓库测试。结论来自调用链、数据形状和写入点，注释只作为被核对的对象。文末列出本次集中验证与仍需验收的范围。

**结论：现有架构已经能作为通用 2D 内容与关卡编辑器使用。** 声明字段、地图与实体、格图、引用、屏幕模块和时间轴，可以用同一套编辑流程组装不同玩法；编辑器画布的格系也不限定游戏实际镜头。横版、俯视、战棋、叙事、卡牌与节奏等已有制作路径，接入各项目的成品模块即可按其声明制作内容。当前要补的是跨项目共用的制作闭环，尤其是保存、复制与撤销、引用验证和坐标一致性。复杂实景中的连续编辑、超大数据量和专业操作效率要按实际工作流验收；本次静态审查没有证明所有规模、所有制作手势都已覆盖。

本文以 **P1** 表示能产生错误正式数据、丢失作者操作结果，或破坏正式流程的缺陷；**P2** 表示明确的正确性、工作流或规模问题；**P3** 表示维护性与呈现问题。标注「已复现」的有运行观察；其余为可按所列步骤验证的静态结论。性能部分为路径与复杂度分析，不是基准测试结果。

## 一、优先修复的实现问题

### F01 · P1：普通保存先写内容，后验证或询问是否写地图

[map_file.gd:816](../../src/ui/map_file.gd#L816) 收集工作副本和身份信息，先保存必要的清单，再调用 [content_form.gd:809](../../src/ui/content_form.gd#L809) 逐条写暂存内容并从暂存移除，最后才进入 [map_file.gd:894](../../src/ui/map_file.gd#L894) 的地图外部冲突确认和写入验证。拿一张已保存地图，新加带内容的实例，再用外部工具修改正式地图；按保存并取消覆盖，内容已经写出而地图仍是旧版。后续某条内容写失败也会留下之前的写入。复制和已落盘地图改名使用 [document_commit.gd:34](../../src/project/document_commit.gd#L34) 登记目标摘要，普通保存没有；现有 [recovery.gd:186](../../src/map/recovery.gd#L186) 登记的是状态证据，不能当作可重放的事务。

**改法：** 复用已有发布计划，把普通保存加入同一条路径。先冻结全部载荷和基线，确认冲突、校验地图和引用，再写任何文件；保留“清单→内容→地图”的发布顺序。只消费正式发布成功的暂存，或记录哪些目标已写与其新摘要，在重试时把摘要一致的目标视为已完成。第一版做到「取消无副作用、部分失败明确且可继续」，不必引入数据库。已落盘内容的即时编辑仍可保留，但要在 UI 和契约中明确它与地图事务的区别。

### F02 · P1：实体粘贴重做可恢复实例，却丢掉刚复制的内容

[selection_ops.gd:758](../../src/canvas/selection_ops.gd#L758) 暂存了克隆内容，[selection_ops.gd:818](../../src/canvas/selection_ops.gd#L818) 只把实例节点传给撤销栈；[undo_history.gd:265](../../src/core/undo_history.gd#L265) 支持把克隆载荷记录在历史中，但只在收到参数时记录。[content_form.gd:787](../../src/ui/content_form.gd#L787) 在保存时清掉未绑定的暂存。触发顺序是「复制带未发布副本内容的实体 → 撤销粘贴 → 保存 → 重做 → 保存」，最后只回来了绑定与内容 ID。**已复现**暂存在无绑定保存后从 1 变 0，把同一绑定加回来仍是 0。即时重做尚未清理暂存时可能正常，不能用这个场景排除问题。

**改法：** 普通实体粘贴传入已生成的内容载荷，和画布自带的复制命令使用同一路径（[editor_canvas.gd:1257](../../src/canvas/editor_canvas.gd#L1257)）。整图快照路径也要附带本次新增的内容载荷，或者改为共同的复合命令。清理与恢复按 `(功能 ID, 内容 ID)`，重做遇到同 ID 已落盘时按摘要识别旧发布，不重新覆盖。

### F03 · P1：裁剪与删除能发布挂空的端口、实例和空间引用

[map_resize.gd:85](../../src/ui/map_resize.gd#L85) 裁对象、瓦片和碰撞，保留地图出口、内容槽和幸存对象的引用；[layer_ops.gd:219](../../src/canvas/layer_ops.gd#L219) 删除层会处理格图层绑定并过滤对象，但不统一分析外部来向；[selection_ops.gd:849](../../src/canvas/selection_ops.gd#L849) 删除实例只核对锁定/隐藏状态。格图删格也只清本格图中的边（[cell_graph.gd:320](../../src/map/cell_graph.gd#L320)）。[map_data_validation.gd:51](../../src/map/map_data_validation.gd#L51) 只检查地图出口容器类型，[map_file.gd:1098](../../src/ui/map_file.gd#L1098) 普通试玩检查提交与摘要，未补做这些语义校验。**已复现**：8×8 图内出口指向 `(7,1)` 的实例端口，裁到 4×8 后对象数为 0，出口仍在，`MapStore.write_error()` 返回空串。

**改法：** 删除、裁剪、层删除、格转换和发放新身份时先生成“受影响目标”列表，查当前草稿及正式文档的入边。UI 允许改接或显式断开；对跨文件引用先报告来向及所需修改。正式发布/试玩复用同一语义检查，画布保留可打开、可修复的草稿。运行时动态生成的 ID 按声明标为外部解析，避免拒绝合法的动态链接。格 ID、格边 ID、层 ID 与端口地址应分别验证。

### F04 · P1：删除保护与运行读取对字段默认值的解释不同

[reference_usage.gd:247](../../src/project/reference_usage.gd#L247) 的资源、屏幕来向扫描直接跳过未存键；[reference_usage.gd:148](../../src/project/reference_usage.gd#L148) 的内容来向只有 `flow_target` 在缺键时取默认，普通内容选择和缺省的嵌套记录不会被展开。相对地，[reference_index.gd:199](../../src/project/reference_index.gd#L199) 的属性扫描能使用声明默认值。**已复现**：有 `fields:{ }` 的工作内容，声明默认指向屏幕 `exit` 或另一条内容时，两种来向查询均返回空；删除保护因此可能放行。显式断线 `{}`、显式空数组和缺键继承默认值不能视为同一件事。

**改法：** 共用有效值遍历器，递归处理记录、条件、步骤、数组、选择和目的地，统一 ID/执行码取值及配对地图上下文。图、删除、复制和发布不用各自重新解释字段；记录每一条来向来自磁盘值还是声明默认。默认目标从未被文档读取时也仍属于声明级引用，应至少在项目检查中报告。读不到的项目范围单列，不能按零来向处理。

### F05 · P1：共享绘制层先创建正式地图，清单取消时变成普通地图

[event_layers_dialog.gd:126](../../src/ui/event_layers_dialog.gd#L126) 点「保存并编辑」先调用 [map_file.gd:38](../../src/ui/map_file.gd#L38) 创建并写入图，再异步保存清单。外部清单冲突时选择取消、清单目录写入失败时，磁盘已有新图，当前清单却没有 `drawingMap`。删图组也只移除清单记录。普通地图菜单将共享画图分组处理（[top_bar_nav.gd:69](../../src/ui/top_bar_nav.gd#L69)），但通用地图目标候选仍收集所有可解析地图（[reference_index.gd:76](../../src/project/reference_index.gd#L76)）；没有全局文档角色区分。图组校验只查形状（[event_layers.gd:38](../../src/project/event_layers.gd#L38)）；**已复现**不存在的 `drawingMap` 不产生结构问题。参照加载遇到失效地址会跳过（[reference_index.gd:14](../../src/project/reference_index.gd#L14)），编辑者无法就地改接旧画图。

**改法：** 创建画图和绑定走 F01 的计划；取消不写文件。给地图索引提供用途筛选：可进入的基础图、绘制文档、按需求可引用的数据图。删除图组提供“解除关联并转为普通地图 / 保留绘制文档待重新绑定 / 无引用后归档”三种明确结果，避免默默变更身份用途。界面显示缺失、重码和目标类型错误并提供重选；清单不认识的新数据仍可打开诊断。

### F06 · P2：普通粘贴混用了世界像素和图层局部像素

[app.gd:598](../../src/app.gd#L598) 传全局鼠标位置，[selection_ops.gd:654](../../src/canvas/selection_ops.gd#L654) 以对象局部 `position` 求组的偏移，[selection_ops.gd:785](../../src/canvas/selection_ops.gd#L785) 把两者相加直接赋给目标父节点下的局部位置。**已复现**：目标层 `offset=[100,0]`、`scale=2`、关吸附，光标 `(150,50)` 粘贴后变成世界位置 `(400,100)`；跨层多选还会混合源层坐标。

**改法：** 复用 [editor_canvas.gd:646](../../src/canvas/editor_canvas.gd#L646) 的局部/画布变换。采集组中心及各实例偏移时使用同一个画布空间；先在世界空间布好组，再将各落点反算到目标层，在局部执行吸附。明确单层模式的“复制到当前层”策略；保层的跨层粘贴走已有跨层工具。测试再加一组不同缩放的源层、视差和多选。

### F07 · P2：整图转换不审计其余空间数据，UI 容易被理解为全图迁移

[map_convert.gd:25](../../src/map/map_convert.gd#L25) 只转换对象锚点和出生点，保留瓦片、碰撞原格号，且没有为已声明的根/层坐标字段、格边和其他随根格系改变解释的值统一生成转换计划。已有按图层瓦片格系单独转换的路径（[tile_layer_convert.gd:4](../../src/map/tile_layer_convert.gd#L4)）；对拥有独立 `tileGrid` 的层，整图转换的统一“瓦片保留需核对”提示也不够精准。一般的游戏自定义参数不应盲改，但已声明的空间引用至少应该检查。

**改法：** 按数据类别报告「保持原世界位置 / 保持格号 / 无唯一转换、需处理」。独立瓦片层先判其有效格系是否变化，转换后按目标网格重新验证格边。空间字段可用声明中的坐标域决定保持策略；不该解释的自定义数据保持原样。预览报告列出受影响的图层和字段，不只给条目计数。

### F08 · P2：导入外部图换了地图码，未处理原图自身的显式引用

[map_file.gd:745](../../src/ui/map_file.gd#L745) 的导入读取单个 JSON，清除原 `meta.code`，发新码后直接写入。与 [map_store.gd:392](../../src/map/map_store.gd#L392) 的复制计划不同，这条路径不迁移绑定附件，不区分同源自引用与外部项目引用，也不重映射显式原图地图码。导入大部分地形能正常显示，但原图端口、嵌套空间引用或绑定内容可能失效，若码在新项目恰好已用，还可能连去其他地图。

**改法：** 明确区分「仅导入单图结构」与「导入地图及其依赖」。前者列出需重连的引用并提供清图选项；后者用现有复制计划接收源清单与选择的依赖，让目标地图、资产与内容映射可审阅后再写入。避免用字符串全局替换。

### F09 · P2：当前绘制层的预览坐标和表现没有可配置的组合语义

当前编辑参照通过 [editor_canvas.gd:146](../../src/canvas/editor_canvas.gd#L146) 建另一套只读画布，以统一根原点、固定前后关系叠放，并各自计算相机视差（[editor_canvas.gd:129](../../src/canvas/editor_canvas.gd#L129)）。创建时从**当下活动的图**复制尺寸与格系（[map_file.gd:45](../../src/ui/map_file.gd#L45)），没有声明共享内容是屏幕空间、父图世界空间还是某一层的局部空间，也没有按每图设置锚点。它适合同一坐标约定下的共用世界覆盖物；同一结算 HUD 横跨尺寸或镜头完全不同的地图时，编辑器自己的叠图不能证明实际 UI 对齐。

**改法：** 明确两种数据用途：世界覆盖层继续使用地图数据；固定 HUD、菜单和结算优先复用已经有锚点与画幅变体的 `views.layout`。如果两个真实样例需要世界覆盖的每图重定位，再给图组加入简洁的每图实例变换与叠放顺序，编辑预览和游戏请求共享该契约。不需要造第二套屏幕布局。

### F10 · P2：保存草稿不保留暂存条目的完整身份，恢复提示覆盖关键信息

[content_form.gd:838](../../src/ui/content_form.gd#L838) 只导出 `fn_id/cid/data`；[content_form.gd:898](../../src/ui/content_form.gd#L898) 恢复时只按裸 `cid` 找实例，保存却按 `(功能执行码, 内容 ID)` 复核。相同裸 ID 在不同功能目录中合法，旧草稿可能被判成已恢复，实际保存时再被丢弃。[map_file.gd:1055](../../src/ui/map_file.gd#L1055) 显示未恢复条数之后立即用成功状态覆盖。本次没有找到 UI 产生替换型暂存的常规路径，因此 `baseline/expect_absent` 未序列化暂记为接口不完整，和明确的身份/提示问题区分。

**改法：** 草稿、复核和正式保存用同一个暂存行结构，按完整内容键确认绑定归属，给遗留草稿加一次性读取默认；把恢复结果合并成一条可读状态并列出未恢复项目。已有正式文件和与其对应的待保存草稿分别展示。


### F11 · P2：从有偏移或缩放的层生成碰撞，会落在没有地形的地方

[tool_ops.gd:297](../../src/canvas/tool_ops.gd#L297) 拒绝独立瓦片格系，却允许一个使用根格系但有 `offset/scale` 的层；它把源层的格键 `c` 原样写入根碰撞层。地图前景层右移一格后，生成的碰撞仍在没右移的格子。替换模式还会移除不在新结果里的原有碰撞。来源形状和目标形状不同不是取整能普遍解决的问题。

**改法：** 第一版只允许有效静态变换为单位变换的源层；平移且整格对齐的情况可复用已有坐标换算再开放。对缩放、视觉视差或其他不适用的布局，引导选择自由形状/碰撞实体。预览和实际执行共用一个碰撞计划，能同时报告替换导致的删除数量。

### F12 · P2：地图目录缓存既会漏刷新，也会在交互路径频繁重扫

[map_store.gd:141](../../src/map/map_store.gd#L141) 每次索引查询仍列目录并查每张图修改时间；签名只有名字与时间，没有大小，故同秒外部修改时甚至可能在还未进入有大小检查的 [map_store.gd:29](../../src/map/map_store.gd#L29) 前就返回旧索引。普通地图画布每秒查一次出口地图名（[editor_canvas.gd:565](../../src/canvas/editor_canvas.gd#L565)），候选也会复用该入口。这是浏览性能与一致性的问题；本次没有观测到摘要保护的普通地图写入覆盖外部版本。

**改法：** 项目会话拥有一次构建的地图目录索引；编辑器读写后按文件和用途失效，外部变化由目录轮询批量更新，提供明显的「刷新项目数据」。重要发布点直接观察目标摘要。删除保护仍可对当前已变来源做足够严格的校验，不用让纯浏览也每次扫描。

### F13 · P3：笔画撤销先查历史是否为空，首笔尚未结束时无效

[undo_history.gd:65](../../src/core/undo_history.gd#L65) 在 `stroke_end()` 之前因空撤销栈返回。空历史的新图，按住左键涂第一笔不松，按 Ctrl+Z，无法变成该函数描述的「就地结束并撤销」；已有此前历史的情况则能走后面的路径。

**改法：** 先判断文档和恢复状态，再结束有效的当前笔画，最后检查空栈。决定是否结束笔画也应和键盘是否在编辑文本、当前手势是否被模态弹窗接管使用同一套入口规则。

## 三、各类型与视角的制作覆盖

### 判断标准：模块接入一次，内容反复制作

游戏工程侧实现并声明可复用模块，提供资产、字段、引用与出口；编辑器侧用现有画布、表单、流程、屏幕与时间轴制作不同实例，管理引用、撤销、验证和发布。游戏侧实现一次移动平台、战棋规则或卡牌结算，是提供游戏本身的功能，**不要求编辑器为对应类型增加模式，也不要求程序员为每张新关卡再写一份实现。** 如果需求是新玩法规则，扩展游戏模块正常；如果同一模块已经接入，作者做下一份同类内容仍必须改程序或手写 JSON，就要找出究竟是哪种数据、编辑动作或发布流程缺了通用入口。

例如，同一组「放置实体 → 配字段 → 选地图端口 → 保存」操作，可以用于横版游戏的房间出口，也可以用于顶视 RPG 的传送点、战棋的撤离区域。三个项目可以使用不同的触发规则和相机，但同一个编辑器用同一种引用来记录目的地、检查目标、复制实例。规则何时触发由游戏侧决定；目标失效后没有被验证、复制重做丢了绑定，是编辑器应当一次修好、所有项目都受益的问题。

### 视角覆盖：把运行相机和编辑手势分开验收

主画布的格空间用于定位、铺格、选区和保存数据。最终屏幕上的横版、俯视、等距、旋转、伪透视或分屏由游戏决定。同一份内容可以被不同相机读取，不需要为一种取景另建地图格式。项目声明实景能力后，游戏可渲染单帧并返回拾取映射；编辑器已有点选引用、放置资产、起草路径或多边形、移动出生点等入口，见 [实景请求](../../src/project/game_preview.gd#L54)、[拾取映射](../../src/project/frame_picks.gd#L53) 与 [实景放置](../../src/ui/map_game_preview.gd#L121)。

**已有主画布和单帧拾取路径，但没有在任意实景画面中连续刷瓦片、连续拖拽或直接编辑根碰撞的通用工作流。** 这会限制特定编辑动作，不等于游戏不能采用该视角。如果作者能用主画布修改、在实景检查或点选，现有路径就成立。只有任务确实依赖「在最终投影里操作」且这个组合不能完成时，才考虑扩充共享拾取或交互能力，例如把视区和目标坐标面一起交给同一套编辑操作，改动仍走现有撤销和保存流程。无需为每种镜头建立一个工具。

### 怎样区分缺陷、缺口和增强项

- **共用缺陷：优先修。** 已有编辑入口产生不一致或不可恢复的数据，例如同一次保存的内容和地图不同步（F01）、复制重做丢内容（F02）、悬空引用或漏报（F03/F04）、图层坐标转换不一致（F06/F11）。这些问题与游戏类型无关。
- **契约或工作流缺口：先定位失败动作。** 比如某个模块需要作者同时编辑一组关联记录，而现有生成响应只接受一个地图文档；若制作流程明确要求生成时同时交付新内容，作者就得另行创建并绑定。此时针对「生成结果如何包含关联文档」补一个通用能力。仅做一次地图生成再手改的工程，可以继续使用现有入口。类似地，只有作者必须在最终画面区分多个可编辑坐标面，而当前图层拾取与主画布都不能完成任务时，才需要补坐标面选择。
- **已有编辑路径，想更快或更直观：按真实负载决定。** 卡牌已经能作为声明记录编辑，表格批改能降低大卡库的制作成本；曲线可以用点和参数描述时，实景曲线手柄能降低调整成本；一次放置能满足的任务，不需要连续实景笔刷。批改、曲线手柄、高频预览都是可跨类型复用的增强，只有当现有路径实际无法完成重复制作或达不到已确定的规模目标时才排进路线。没有观察到阻塞，就不预建结构。

「通用」可以通过实际任务验收：换一套已接入的游戏模块、格系或镜头，仍用同一编辑器制作下一份内容并发布，整个过程无需新增专用编辑代码。有新需求时先问现有声明和操作能不能完成，再判断卡住的是玩法接口、数据表达、作者操作还是发布。这样会得到少量清楚的共用改进项，而不是一张按游戏类型排的功能清单。

## 四、架构与性能评估

整体方向正确：用 Godot 自带渲染编辑常规格，使用自绘补足任意斜基/三角；以 v7 JSON 固定内容身份；通过声明、稳定 ID、功能码和外部进程把游戏执行从编辑器中分出去。独立瓦片层、GridSpace 统一几何、显式复制计划、可复用的字段控件、时间区间索引、参考画幅与屏幕模块，均值得保留。不能把“每个模块已有独立文件”当作接口封装已经做完。

| 模块群 | 现状和判断 | 推荐的最小改造 |
| --- | --- | --- |

### 可定位的性能热点

- **主画布：** 三角/斜基瓦片已有块几何和视区裁剪，不应退回每格节点。内容中列对实体次序和瓦片行有缓存，但碰撞仍枚举全部占用格，内容预览瓦片绘制也逐条检查（[content_preview.gd:303](../../src/ui/content_preview.gd#L303)、[content_preview.gd:322](../../src/ui/content_preview.gd#L322)）；画布辅助绘制也枚举可见层上全部实体（[canvas_draw.gd:150](../../src/canvas/canvas_draw.gd#L150)）。大地图在编辑、平移时应复用原有分块几何/空间查询，只有视区附近的实体和碰撞参加命中与辅助线；给复杂几何按对象修订缓存画形。
- **参照与大型形状：** [editor_canvas.gd:146](../../src/canvas/editor_canvas.gd#L146) 每次刷新完整销毁并重建所有参照画布；[object_geometry.gd:156](../../src/map/object_geometry.gd#L156) 的填充按顶点高度分条，复杂形状数据需观察编辑时重复更新的代价。先按地图码+文档版本复用参照渲染，粒度保持在画图/图层；需要时再做几何缓存。多个同应用画布已有图集缓存，继续复用。
- **发布、大图与历史：** `extract()` 枚举图的瓦片、对象、碰撞；整图快照编码/解码与重建的开销随图规模，80 步的步数上限没有限制内存体积。保留混合差量的好设计，给大型区域/布局工具换成事件差量或记下被改分块，基准确认后再设置历史内存预算；保存时一次冻结，可把编码或已验证快照交给后续路径复用。避免同时维护三套镜像。
- **项目扫描：** 内容读取每次会读字节和取摘要以保证写入基线；图构建、列表候选与删除操作却经常读取同一批来源。新索引只缓存每文档需要的元数据和出边，以项目变动更新；会写入的目标继续检查真实摘要。F12 的「浏览可稍延迟，提交必须见最新」把性能与正式数据正确性分开。
- **实景协议：** [game_preview.gd:5](../../src/project/game_preview.gd#L5) 对请求与生成文档限 4 MiB、最长约 12 秒，并为每个请求起游戏进程；[map_game_preview.gd:339](../../src/ui/map_game_preview.gd#L339) 会带当前地图及解析的绘制层。它适合可重现的单帧，不适合高频拖拽或整大世界。优先把已保存的大数据改成按摘要引用，草稿传修改过的文档/分块；经过两种实际游戏验证仍有负载需求时，可选维护一个可取消/限时的常驻取景进程，保留一次性协议兼容。预览快照按稳定引用解析，不能为了减少体积让预览悄悄变成旧盘面。

性能验收建议记录首开、普通笔画、平移、范围复制、撤销、首次关系图、再次打开候选和实景响应的 p50/p95 与内存峰值。先做一份 10 万瓦片、1 千实例的关卡样本，再做百图与千内容的项目样本；这些是验证用的目标规模，不是本次测出的上限。普通交互与整图/全项目任务分别定预算。优先消除明确随全图、全项目增长的热路径；没有实测瓶颈的地方不加预防性缓存。

## 五、改造顺序与出门验收

| 阶段 | 交付物与判定标准 |
| --- | --- |
| **第一阶段：让发布可信** | 修 F01–F06、F11，落实同一套有效引用遍历和可恢复发布计划。验收：取消冲突后磁盘各目标不动；部分失败可重试；删带入边实例可改接或阻止发布；撤销→保存→重做保持克隆内容；带失败清单的图组保存不留下普通图；图层变换前后的粘贴和碰撞一致。 |
| **第二阶段：验证并补齐共用制作闭环** | 修 F07–F10、F12，修正规范中过度承诺的表述。给作者一组成品控件、地图对象和流程，验收能否只用编辑器新增第二张关卡和第二份结算页面，保存、重开、试玩并定位引用错误。项目级预发布诊断、模板与批量操作按实际失败步骤和负载排序。 |
| **第三阶段：用不同制作任务验同一契约** | 选取空间关卡（横版或俯视）、格网或数据内容（战棋或卡牌）、时间或非标准取景（节奏或旋转/分屏）等有代表性的样本。统一验收「接入一次 → 制作第二份内容 → 修改、重开与发布」；切换格系或更换镜头时检查既有编辑数据和引用是否仍可用。只有发现现成路径做不成的作者操作或实测规模问题，才安排对应的共用补充。生成后再合并人工修改等高级流程单独验收，按项目需求排期。 |

对外可准确定位为：**一套面向多种玩法与视角、由游戏侧模块驱动的通用 2D 内容与关卡编辑器。** 游戏侧提供规则、表现和可编辑接口，作者在统一的地图、内容、屏幕与时间轴中组装。对已支持的编辑动作如实说明；专业工具和规模上限用验收结果说明。
