## 1. 结论

优先修复三件事：区域移动丢瓦片、提交可能覆盖新出现的内容文件、草稿恢复无法还原补发身份码。
现有声明驱动、混合层栈、独立内容文件和差量撤销的方向正确。当前风险主要来自状态归属不清：
地图节点、载入时字典、表单暂存和磁盘文件分别被不同入口当作当前数据。

## 2. 架构与数据流

| 环节 | 当前实现 |
|---|---|
| 项目接入 | `editor.tscn` 挂 `app.gd`。清单校验后在内存合并内置声明、补发身份码、扫描资产目录。关卡/内容/资产视图共享这份清单。 |
| 地图编辑 | `MapStore` 读地图，`EditorCanvas.load_data()` 建图层、瓦片、碰撞、实例、出生点。瓦片/碰撞/实例值主要在活体节点；地图 meta 与载入原始行在字典里。保存与草稿经 `UndoHistory.extract()` 重新合成。 |
| 内容编辑与撤销 | 实例绑定功能，绑定指向独立内容文件。新内容随地图暂存，已有内容的普通字段可即时写盘。历史同时保存整图快照、格差量、实例差量和会写回磁盘的内容差量。 |
| 交付与试玩 | 地图保存与内容页保存走 `DocumentCommit`（清单 → 内容 → 地图）。资产页单独写清单。改名/整图复制在 `MapStore` 各自编排。试玩先提交再启动游戏侧声明的进程。 |

规则实现、行为、资源生产在游戏侧；编辑器负责摆放、绑定、填写公开字段与组织步骤。
这条边界适合通用 2D。空间摆放链最完整；内容表单、帧拍时间轴、具名参考画幅已有实现。
有限格图目前主要用于引用与定位，试玩依赖外部进程。**现有代码足以说明编辑器能表达多类 2D 内容，
但不足以证明任意类型、视角和制作流程都已贯通。**

## 3. 问题清单

### P0 · 作者数据可能丢失或被覆盖

**1. 移动有瓦片的区域会清掉源瓦片，却不写目标瓦片。**
左键松手进入 `_finish_region_move()`。该函数先擦源格，目标瓦片循环缩进在
`if li2 < 0: continue` 之后——有效层跳过整个分支，无效层提前退出，两种情况都不写目标瓦片。
碰撞和实例照常移动，界面仍报成功。同路径碰撞快照只带坐标、类型、形状，漏掉正常保存保留的扩展字段。
建议：先修控制流；让移动先解析完整源/目标载荷，全部可应用后再擦源；保留现有覆盖规则与一次撤销粒度。

* `src/canvas/canvas_input.gd:347`
* `src/canvas/region_ops.gd:134`
* `src/canvas/region_ops.gd:61`

**2. 提交计划冻结了内容载荷，执行时却重新读取当前表单。**
`prepare()` 把载荷放进目标，`apply()` 只把 `cid` 交给表单，地图由钩子再次从画布提取，会话 token
未参与执行复核。可静态确认的覆盖场景：新内容预留 ID 时尚无文件，另一写入方在 `prepare()` 前创建
同路径有效文件，提交会把这个新文件当基线，再用暂存数据覆盖。内容冲突分支还会清掉待提交日志，
即使前序目标已写入。
建议：目标明确区分“预期不存在”和“预期是某摘要”；实际写入使用计划中的路径与载荷；部分完成时保留日志。

* `src/ui/map_file.gd:789`
* `src/project/document_commit.gd:14`
* `src/project/document_commit.gd:62`
* `src/ui/content_form.gd:674`

**3. 草稿保存了对新身份码的引用，却只保存“清单待补码”标志。**
清单装载时在内存补发缺失码。草稿保存地图与暂存内容，但没有保存这次补发的实际映射。
若清单从未落盘，重启时发出不同码，恢复草稿只重新置位 `_codes_issued`，原引用仍指向旧码。
建议：草稿同时持有清单基线（或补发映射），恢复时按基线合并；有冲突时保留原草稿供复核。

### P1 · 保存、身份和编辑语义不一致

**4. 空白新图可提示提交成功，但没有正式文件。**
新建空图走普通装载，装载后通常干净。`prepare()` 只在地图脏时加入写入目标，首次保存可能返回
“无待写改动”。试玩另有检查文件并补存的分支。
建议：把“从未保存”作为独立文档状态；显式保存与试玩走同一创建路径。

**5. 内容写入结果和内容历史各有一处契约错误。**
演出面板期待布尔，转发函数声明 `bool` 却实际返回 `"ok"/"conflict"/"fail"`。
内容撤销把读出的字典重新序列化，再用原始文本摘要守卫重做；手写 JSON 仅缩进不同时，

建议：显式传播结构化结果；撤销成功后记录实际写回摘要供重做使用。

**6. 引用唯一性和删除检查取决于调用入口。**
`ReferenceIndex.resolve_map()` 先匹配图名再查码与撞码。一张图名恰好等于另一张图码时，
按码存储的引用会解析到前者。内容路径按功能与内容 ID 寻址，但暂存表和部分克隆映射只按裸 ID。
删除已覆盖活体、磁盘、草稿并在确认后复查，暂存入边却只比较顶层字符串，漏掉步骤与结构化字段。
建议：统一 `MapKey`、`InstanceKey(地图码, 实例码)`、`ContentKey(功能ID, 内容ID)`；
候选、克隆重映射、审计、删除入边由同一遍历器提供；破坏性操作遇歧义或读取不全即停。

## 4. 结构、耦合与可维护性

`app.gd` 与 `EditorCanvas` 的问题不是“文件太长”，而是它们仍是控制器之间过宽的读写面。
拆分后的方法大量在宿主间转发私有成员。`DocumentSession` 在提交时临时创建并引用 UI 持有的暂存表。
`ReferenceIndex` 与 `ProjectAudit` 相互依赖。地图行/节点转换放在 `UndoHistory` 里，普通装载也依赖历史模块。
继续按文件长度拆分不解决这些依赖。

重构顺序：

1. **收口局部缺陷**：区域移动、空图首次保存、演出写入结果、显式正交。
   把地图行/实例行/碰撞行的编码从历史模块提取为共用转换，先让保存、区域、剪贴板复用。
2. **`DocumentSession` 持有持续存在的文档工作副本**：项目/文档身份、代次、修订、已接受基线、
   暂存、未保存状态。第一步仍可从活体画布提取地图。
3. **`DocumentCommit` 执行已确认的文件计划**：UI 负责收集值、展示计划、确认；执行层按计划写并返回
   逐文件成功/跳过/冲突/失败。先接保存与试玩，再收拢改名、复制、清理的重复编排。
4. **审计、预览、撤销消费同一份数据**：引用索引由磁盘快照 + 会话覆盖层生成；画布与预览共享几何；
   撤销记录并应用变更，序列化由转换层负责。

## 5. 性能与调试

以下为源码可见成本，卡顿幅度取决于项目规模。

| 路径 | 静态证据与建议 |
|---|---|
| 跨图引用、自检、删除 | `resolve_map()` 一次调用可先列目录再逐图读取查撞码；审计对跨图字段反复解析目标；删除的可读性检查与入边枚举分别读取内容。优先在一次查询/操作中构建地图码、实例码、内容 ID 与入边索引。 |
| 内容预览、三角瓦片、碰撞 | 预览瓦片缓存按全局 `map_rev` 失效，实例修改也会增加它；悬停重画仍遍历绘制各层瓦片；三角/碰撞自绘每次刷新遍历各自整层。先分离地形与高亮、按层码与数据种类失效，再按可见区域裁剪。 |
| 多文件写入与试玩 | 每写一个目标都读写整份提交日志，大批量操作重复序列化同一目标表；试玩在主线程同步 `tasklist`，日志尾部读取整文件。先分离目标表与进度记录；进程查询离开主线程并限制日志读取量。 |

调试上优先保留**同一操作的完整结果**。草稿恢复先报未恢复内容条数，随后立刻用成功文案覆盖。
建议状态栏只放摘要，详情保留文档代次、目标路径、失败阶段、已写文件与剩余项。

## 6. 待确认问题与假设

- **保存语义**：方案按“已有内容即时保存，新内容随文档提交”。需确认“放弃地图”是否撤回同会话已即时写盘的内容。
- **外部写入**：假定游戏工具、人工编辑或另一编辑器实例可能在会话中改正式文件。
  文件不存在、无法读取、内容已变化仍需分别表示。
- **身份与空间**：需确认旧图名兼容范围，以及格边在空格、边界、整图复制、区域移动后的语义。
  异形拓扑的渲染等价性、Godot 返回类型错误表现、平台文件替换行为留作运行层确认。
- **通用 2D 范围**：地图空间、屏幕参考、时间轴三种制作场景可组合，优先级取决于实际接入项目最早断点。
  当前只有编辑器源码，游戏侧实际消费行为无法由此确认。
