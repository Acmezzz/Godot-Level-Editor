# 通用 2D 关卡编辑器初版审查

本报告记录初版行为、源码证据和问题编号。后续开发以[统一实施方案](V1-IMPLEMENTATION-PLAN.md)的任务、目标行为和验收为准。先从本报告 §6 查任务，再在实施方案中查实施步骤。第 3、4 节保留初版发现，修复后以验收记录更新状态。

## 1. 范围与判定标准

- 审查对象为 `src/` 当前工作树、`EDITOR_FEATURES.md`、`GAME_SIDE_STANDARD.md`。实现以入口、分支、序列化和实际调用链为证据，模块注释与两份文档作为待核对陈述。
- 本次为源码静态审查，覆盖入口场景与 `app.gd`，以及 `canvas/`、`core/`、`map/`、`project/`、`assets/`、`content/`、`ui/` 的相关模块和跨模块调用。下文场景用于复核或回归验收，未启动编辑器、运行测试套件、读取游戏工程或测量性能。游戏侧契约只审编辑器实际产物及规范示例的自洽性。迁移脚本是否幂等和文档所列测试数量超出本次范围。
- `P0` 表示阻断冷启动或项目切换入口。`P1` 表示可能丢失或错误覆盖数据、破坏关键工作流。`P2` 表示可触发的功能错误、契约错误或常用流程缺口。`P3` 表示局部体验、维护性或待实测的性能问题。
- 「具备」要求设计者能在编辑器中独立完成配置、保存重开和持续修改。「受限」表示可以用现有数据组合表达，但编辑效率或校验精度不足。「缺失」表示关键数据或编辑操作需要手写文件、改游戏代码或另用工具。
- 游戏工程提供两类制作对象。资产供地图摆放并负责视觉，功能实现游戏行为并声明可编辑的内容接口。地图记录摆放，实体实例承载功能绑定，内容文件记录公开字段和编排数据。编辑器只能摆放、绑定、填值和编排已有功能。功能源代码和运行时执行归游戏工程。

## 2. 总体判断

项目已经形成了清晰的常规地图工作流。一个了解自己数据契约的游戏工程可以提供图集、实体、功能及步骤定义，设计者在画布和内容工作台中把它们编排为关卡。资产发现、声明式表单、实例身份与独立内容文件是值得保留的基础。

按「资产摆放 + 功能内容」评估，初版已有常规地图制作的通用基础。对话分支可用内容引用表达，卡牌可用视觉资产与效果功能表达，演出和波次可用已有步骤表达。覆盖上限取决于游戏是否公开了所需参数，以及编辑器能否把这些参数选、填、关联、编排并可靠落盘。横版、俯视、等距等空间任务还取决于地图坐标与呈现能否准确编辑。

两个入口问题应先处理。E00 影响首次进入项目，D05 影响同进程切换项目。随后优先验证地图的读写回环、缺失素材时的数据保全、资产发码落盘、复制后的内容隔离，以及悬空引用清理。准确记录当前行为后，再把承诺与实现同步修订。

后续扩展以具体制作任务为单位，例如「复制带互相引用的房间并独立修改副本」，由游戏模块实现运行时效果。

## 5. 2D 制作任务覆盖与能力边界

### 5.1 用设计者实际完成的任务衡量覆盖

先确认游戏工程是否已经提供该功能，以及它公开了哪些内容字段。功能缺失或所需字段未公开时，由游戏工程补实现或声明。编辑器的覆盖评估针对已经声明的数据。

每条覆盖用例依次检查**游戏侧声明、界面录入与维护、保存重开、试玩**。保存数据必须保留正确的坐标、字段、引用和编排。已有字段能录入但缺少高效视图时，记录操作成本。已声明数据无法填写、重开或正确引用时，记录具体失败步骤。覆盖状态与[实施方案 §1](V1-IMPLEMENTATION-PLAN.md#1-覆盖目标与优先级)使用同一套判定。

视角与玩法分开衡量。视角验收投影、锚点、遮挡和命中。玩法验收模块能否按所需粒度组装。例如俯视射击与俯视战术可以共用坐标系，对前者重要的是波次时间与路径，对后者重要的是地形属性、分区和拓扑。同一个敌人模块可以交给游戏侧实现，两类内容的配置入口仍有不同要求。

### 5.4 决定覆盖上限的源码约束

- **空间坐标按项目取默认值。** 画布从清单读取 `tileSize`，投影取第一个非正交瓦片资产的 `gridProjection`。混用只警告，地图本身没有投影选择。六边格反算会取最近中心，关吸附也不能复用正交投影的完整亚格语义。图层栈只解决绘制先后，战术所需的逻辑高度和通行层有独立建模需求。见 `src/canvas/editor_canvas.gd:458`、`src/canvas/grid_space.gd:47`、`src/project/manifest_validation.gd:55`。
- **时间轴的时间基只覆盖显示和编辑步进。** `at/duration/track/blocking` 能描述简单事件区间。缺少帧率、音乐速度映射、帧图对齐或播放头。帧图预览固定 8fps，首选缩略图存在时不会装载帧序列。游戏侧导出的姿态和波形需要预览接入口。见 `src/content/step_timeline.gd:18`、`src/ui/timeline_view.gd:21`、`src/ui/steps_panel.gd:268`、`src/canvas/entity_node.gd:118`、`:377`。
- **关系的作用域分散在控件和操作中。** 实例选择器查本图，地图选择器独立存地图码，画布另用固定键绘制连线。表单可选择内容、资产、层和音频，但复制及自检没有共用的引用描述。C1–C3 统一作用域和重映射，E2 用同一结果显示引用。见 `src/ui/content_editor.gd:506`、`src/ui/content_form.gd:209`、`src/canvas/canvas_draw.gd:125`、`src/project/project_audit.gd:15`。
- **功能内容以实例绑定为入口。** 对话、卡牌和演出沿用同一套字段与步骤。初版控件支持有限的标量、一维数组和选择项。若某个功能公开了可重复的混合字段，先看已有步骤能否表达。只有现有字段和步骤都无法填写该公开数据时，才考虑扩充通用控件。见 `src/ui/content_editor.gd:279`、`src/ui/content_form.gd:371`、`src/ui/field_widgets.gd:180`、`src/project/manifest_validation.gd:16`。
- **图层与区域复用有各自的状态。** 图层参数和 `zPolicy` 已有数据，`sortAnchor` 有标记但仍需验证真实排序。区域剪贴板能搬运布局，换图会清空。B2 修排序，C2 校验整组负载、层映射和内容身份。可反复利用的房间保存为普通地图，按 C2/E3 复制。见 `src/canvas/layer_ops.gd:112`、`src/canvas/canvas_draw.gd:175`、`src/canvas/region_ops.gd:83`、`src/canvas/editor_canvas.gd:181`。

### 5.5 在已有资产和功能之上补齐编辑能力

实施目标为四个编辑面板。关卡画布负责摆放、几何和空间选点。内容负责实例绑定、公开字段和引用。演出从当前功能进入，默认步骤列表，可切时间轴、停靠或展开。资产图鉴负责搜索、预览、摆放入口和使用检查。顶栏保留「关卡」「内容」「资产」三个一级入口。跨面板共享保存、问题定位与试玩，配套任务为 E1/E3。

先复用现有输入、选择、内容引用和步骤列表。功能声明决定可编辑字段、可用步骤和条件链。表格可批量填写现有字段，图可展示现有内容引用，时间轴可精确调整现有步骤。各视图使用同一份内容数据。对话、卡牌、谱面和任务沿用实体绑定的功能内容，模型保持两类制作对象。

遇到实际录入困难时，按已公开的字段补通用操作。跨图目标可联动选择地图与实例。形状值可用画布把手编辑。时间值可按声明的单位精确输入并与参考帧对齐。编辑器负责类型、范围、引用和保存检查。游戏工程负责解释输入并执行镜头、判定、寻路、生成和界面行为。实际效果由游戏试玩或游戏侧提供的预览数据验证。

对 AI 也沿用这套接口。开发新功能时，在游戏工程实现行为并声明可编辑项。制作内容时，使用同一份清单选择资产和功能，只生成摆放、绑定和字段值。这样一套功能实现可以供多个关卡、实例和内容条目复用。

### 5.6 组装能力的验收边界

矩阵第二列描述源码已有的数据表达和操作。涉及入口、保存及引用的问题见第 3 节，需要先复核才能确认交付流程。验收以游戏已提供功能和声明为前提。确认设计者能完成摆放、填写、引用、编排、保存重开与试玩。对话节点和卡牌效果沿用现有功能内容。支持分支、招式或谱面的操作缺口，应具体落到哪个公开字段或步骤还无法可靠编辑。

### 建议优先复核的操作

1. 从冷启动进入有效项目，再执行 A → 项目列表 → B。确认编辑界面完整，瓦片与摆放物列表均可进入，自动碰撞能明确选源层。对应 E00、D05、E01、E03。
2. 保存并重开一张有原样、旋转和翻转瓦片的地图。临时移出其中一个图集并重新打开，确认未解析瓦片和实例身份可恢复，或编辑器明确禁止覆盖。对应 D01、D02、D09。
3. 扫描新资产后直接从关卡页保存并重启，再改名并重开。核对地图仍解析同一个资产 ID。对应 D04、D06。
4. 复制一组互相引用且绑定演出的实体。改单个副本的字段与时序后重开，核对副本引用到新组、原组参数不变。对应 C01、C02、C05。
5. 生成悬空引用报告，把其中一个字段修好并保存，然后执行旧报告里的清除操作。检查修好的字段仍在，当前图与磁盘一致，写失败有对应反馈。对应 D07。
