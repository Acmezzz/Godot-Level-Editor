# 2D 游戏编辑器：Ponytail Ultra 源码审查

基线：`5fbc93b`，2026 年 11 月 28 日。审查对象为 `src/`：121 个 GDScript 文件（40,056 行，含注释及空行）和启动场景。仅用协议文档、导出配置和现有测试交叉核对行为。本轮只出审查结果，未改产品代码。

## 项目做什么

游戏侧声明资产、功能与执行语义；编辑器负责制作地图、摆放、屏幕、引用、内容和演出，把同一套数据交给游戏执行。人通过 GUI 制作，AI 通过本机 MCP 看项目、编辑草稿、预检和发布。本次以一个主编辑器进程、单人或人和 AI 交替操作，120 张以上地图、1,152 件资产、百余功能、数千实例、长演出与反复编辑的长会话为验收量级。

**结论：核心分工成立，继续用现有架构。最先解决的是正式数据的可信度：预检是否看懂同一份数据，实际写盘是否对应返回的状态。** 本轮列出 8 项需要修复、5 项值得优化、1 项可直接清理。问题都可以在现有模块边界内处理，不需要按游戏类型加适配。

## 需要修复

### 1. 错误的演出内容通过预检并进入正式游戏数据

- **位置**：[MCP 内容写入](../../src/mcp/edits.gd#L343)、[发布校验](../../src/mcp/workbench.gd#L361)、[时间轴解析](../../src/content/step_timeline.gd#L19)。
- **实际问题（已复现）**：给合法功能写入 `fields: {"DURA":"oops"}`，其中 `DURA` 声明为整数；同时写入 `steps: [42, {"step":"ZZZZ","fields":{"UNKN":1}}]`，`ZZZZ` 未声明。实际 `apply_changes` 接收、`validate` 返回 `valid:true, issues:[]`，发布预检通过；正式写入后的 JSON 保留了数字条目和未知步骤。清单字段类型只用于声明与控件，发布检查没有验证已写入的值；时间轴也会跳过非对象条目。
- **最小修法**：用现有字段声明和步骤执行码做一次内容值校验。检查已填写的已知字段、步骤行、步骤码、步骤字段及合法时间值。旧文件仍可读出来修，未知的游戏扩展键仍可保留。让正式项目检查和 MCP 发布共用判断，并给出 `content/功能/ID.steps[i]` 级路径。不要把开放的游戏字段换成硬编码的类型名单。
- **不改的后果**：「校验通过」时仍可能出现跳步、错值或游戏读档失败。现有时间轴单测和 MCP 正常路径没有覆盖这条发布闭环。

### 2. 内容分支传了配对地图，引用检查却没沿这条关系走

- **位置**：[字段引用采集](../../src/project/reference_index.gd#L199)、[内容地图上下文](../../src/project/spatial_reference_check.gd#L97)、[人工删除检查](../../src/project/spatial_reference_check.gd#L48)。
- **实际问题（已复现）**：内容 A 的 `branch` 指向内容 B，声明 `contentMapContext: "paired"`，配对地图为 Beta；B 的本图字段引用 Beta 的实例 `M001`。删除 `M001` 时人工保存不拦，MCP 验证 B 仍返回 `valid:true`。引用记录只为空间引用填 `paired`，传播只认 `inherit`；没有上下文时，本图实例预检跳过存在性检查。
- **最小修法**：让引用采集在同一级字段中解析配对地图，然后在现有「内容键＋地图码」队列里沿 `paired` 走到指定图；保留 `inherit` 原行为。把已填写但无效的配对图定位到源字段，继续使用现有去重，别再维护一份图关系表。验收时用两张有不同实例的地图和一个循环分支，确认进入正确图、删除正确拦截。
- **不改的后果**：分支编辑看似完成，实际进入关卡时才发现目标不存在，人工和 AI 两条制作入口都漏检。

### 3. 正式文件已发布，但失败返回声称草稿版本写不成，重试也卡住

- **位置**：[草稿发布收尾](../../src/mcp/drafts.gd#L297)、[发布后重载](../../src/mcp/workbench.gd#L512)。
- **实际问题（故障注入复现）**：让正式文件目录保持可写，仅让发布后用于清空草稿的新快照路径无法替换。正式内容已写入，待处理回执却已清除，工具返回 `error: 无法写入草稿版本` 并带上实际文件与已发布版本。工具不重载会话；用同一版本重试时，刚写出的文件反过来被当成冲突。
- **最小修法**：以正式文件达到计划摘要作为发布结果；把草稿整理当作可重试的收尾。正式数据成功就更新会话并返回明确的已发布状态，收尾失败单独报告；记录已完成版本，允许同一请求只重试收尾。复用现有 pending 回执，直到草稿状态收齐，别新增事务系统。
- **不改的后果**：人或 AI 看见失败，磁盘却已经变了，下一次可能误建新草稿、重复操作或继续依据旧状态工作。

### 4. MCP 调整功能行顺序，却没有更新游戏读取的顺序值

- **位置**：[MCP 绑定编辑](../../src/mcp/edits.gd#L307)、[人工重排绑定](../../src/ui/fn_bind.gd#L438)、[数据协议](../GAME_SIDE_PROTOCOL.md#L710)。
- **实际问题（已复现）**：初始 A 的 `order=1`、B 的 `order=2`。MCP 把 B 移到第 0 行后，磁盘候选是 `[B(order=2), A(order=1)]`。人工路径会重排 `order`，MCP 新增、删除和移动没有做同一件事。
- **最小修法**：两个入口共用一次重编号。把对顺序的编辑解析为同一个位置；已有 `data.order` 的兼容调用可换算为位置，和 `index` 冲突时报告错误。无需更换绑定 ID 或改游戏读取方式。
- **不改的后果**：编辑器显示 B 先执行，按协议读取 `order` 的游戏执行 A 在前。若 A 是显示 HUD、B 是切图或初始化状态，结果会明显不同。

### 5. 演出的批量写入没有可撤销记录

- **位置**：[段落批量调时](../../src/ui/steps_panel.gd#L884)、[步骤写入](../../src/ui/steps_panel.gd#L723)、[普通内容字段撤销](../../src/ui/content_form.gd#L671)、[快捷键入口](../../src/app.gd#L337)。
- **实际问题（已复现）**：改动已发布演出，步骤写入返回成功，重读磁盘可见新步骤，但撤销栈还是空的。批量调时、增删、拖块和粘贴都经同一个步骤写入口，也不记内容撤销；在地图工作区快捷键还可能撤掉上一笔无关的地图操作。
- **最小修法**：步骤写入成功后复用现有内容变更条目，记一次前后正文和摘要；段落调整算一步。演出获得焦点时先路由到该内容，项目内容无地图时也能撤销，不为演出另造历史格式。用「成功写入、撤销、重做、外部改写后不覆盖」覆盖一条闭环。
- **不改的后果**：误动几十步后只能手工重排或找历史文件，在地图上按撤销还可能改到别的对象。

### 6. 图组使用相同排序值时，普通地图与图组参照显示相反

- **位置**：[整组排序函数](../../src/project/event_layers.gd#L20)、[以图组为当前文档的参照](../../src/ui/map_file.gd#L126)、[画布层次分配](../../src/canvas/editor_canvas.gd#L152)。
- **实际问题（已复现节点顺序）**：图组 A、B 都用合法的 `drawOrder=1`（也是默认值），普通地图明确顺序为底图、A、B；编辑 B 并叠加底图参照时，A 被分给比 B 更高的 Z 值。相减得 0，画布把 0 当作前景。两个组的图形交叠时会判断错遮挡。
- **最小修法**：以 `drawing_stack()` 已给出的完整顺序算相对于当前组的位置，别再对 `drawOrder` 做减法。同值仍合法，保留整组排序和图组碰撞作用域。
- **不改的后果**：一组内容在参照画面里盖住另一组，回普通地图后却被盖。通过清单或 MCP 新建组时容易遇到。

### 7. 合法省略图层的地图，MCP 筛选会报运行时错误

- **位置**：[地图对象校验](../../src/map/map_data_validation.gd#L200)、[画布默认落层](../../src/core/undo_history.gd#L647)、[MCP 对象和绑定查询](../../src/mcp/workbench.gd#L306)。
- **实际问题（已复现）**：一个实例有资产、坐标和码，未写可选的 `layer`。地图通过写入校验、画布回落第一层；MCP 的 `query_content(kind=objects, layer=第一层)` 却触发 `Invalid access ... 'layer'`，返回空字典。绑定查询的结果也直接取 `item.layer`。
- **最小修法**：查询和加载使用同一个有效图层默认值，筛选和返回都按这个值。保留老图和生成器无需显式写出每个实例的默认层。
- **不改的后果**：AI 用图层做筛选时，会丢掉整个结果，而不是单独少一条记录或收到一条可定位的错误。

### 8. MCP 可以新增已停用资产的实例

- **位置**：[MCP 实例写入](../../src/mcp/edits.gd#L267)、[画布放置规则](../../src/canvas/editor_canvas.gd#L1872)、[停用资产判断](../../src/assets/asset_decl.gd#L189)。
- **实际问题（已复现编辑处理器）**：给实体声明加 `disabled: true` 后，画布的放置判定为否，但 MCP 的 `instance.put` 处理器仍然新建实例并分配 ID。新建检查只看资产是否存在和是否属于瓦片。瓦片笔刷也只查形状，存在同一遗漏（源码确认）。
- **最小修法**：MCP 在新增实例和绘制新格时按画布规则拒绝停用资产。保留旧摆放的读取、修改和移除；资产恢复启用后仍使用原 ID。用同一个停用声明覆盖「拒绝新放、能处理旧摆放、启用后能新放」。
- **不改的后果**：资源因删除文件或退役被停用后，人看不到可放置入口，AI 却仍能将它加入新关卡。

## 值得优化

### 9. 每次普通内容写盘后，下一次取缩略图都可能重新加载并留住整套纹理

- **位置**：[缩略图缓存](../../src/app.gd#L263)、[全局写盘版本号](../../src/map/map_store.gd#L314)、[调色板取用](../../src/ui/palette_panel.gd#L365)。
- **实际问题（已复现）**：缓存以项目目录和 `project_rev` 为键；地图、内容等普通写盘也加版本号。每次写一个无关文件后取缩略图，缓存代数依次变成 1、2、3、4、5、6，直到切项目才清空。新代会重新解码图片并创建纹理，旧代一直被引用。
- **最小修法**：只保留当前项目的一份缓存，资产缩略图变更时失效；最好按实际缩略图路径复用。别将所有保存事件套进缩略图键，也无需引入通用缓存框架。
- **不改的后果**：中后期频繁「改内容 → 换图或开资产浏览」会反复读图，长会话占用的内存和纹理资源持续增加。

### 10. 热路径取一个资产，实际会重新哈希完整资产表

- **位置**：[资产查询](../../src/assets/asset_decl.gd#L22)、[声明指纹](../../src/content/declaration_pool.gd#L6)、[MCP 对象循环](../../src/mcp/workbench.gd#L318)、[引用扫描](../../src/project/reference_usage.gd#L186)。
- **实际问题（已测量）**：1,152 条模拟声明，预热后重复取 5,000 个声明，原路径约 444–630 ms，一次取得声明表后按键查约 1.2–1.4 ms。这个数字是 Windows 本机 Godot 的循环对照，不能直接换算成整界面延迟。资产表缓存命中也要算完整哈希，多实例扫描把这个成本乘了很多次；MCP 分页在遍历和建行以后才切片。
- **最小修法**：先在对象查询、引用扫描和绘制遍历外取一次声明表；持有归一化声明的调用直接使用 `label_of_decl`。功能池同样先移动已查明的高频调用，等测到其它热点再改。别先引入跨进程索引或后台线程。
- **不改的后果**：资产数和实例数一起涨时，一次查询、图谱扫描或画布更新会花大量时间验证同一张表没变。

### 11. 草稿历史拆开了文件，但每一版仍重复保存全部已改地图

- **位置**：[草稿追加与快照](../../src/mcp/drafts.gd#L162)、[发布后回收](../../src/mcp/drafts.gd#L331)。
- **实际问题（已测量单版体积）**：一个含 12,000 格的地图快照序列化约 1.00 MB。草稿改过十张同规模地图后，即便下一步只改一项内容，每个新版本也会再次写十张地图；若继续做 100 次，单这一段历史约 1 GB。这是按程序写入方式推算的体积，未模拟写满磁盘。
- **最小修法**：保留现有版本号和游标，把每版拆成小清单和各文档正文；未修改的正文沿用上一版文件，发布/丢弃时回收无引用正文。不要引入数据库，也不需要以长补丁链恢复一个任意版本。
- **不改的后果**：AI 长时间分批制作多图时，改一个字段开始承担十张图的写盘成本；版本独立可读已解决随机读取，但没有解决重复写入。

### 12. 自定义格层的瓦片与实体不能做到同层逐格穿插遮挡

- **位置**：[画布选择自绘瓦片](../../src/canvas/editor_canvas.gd#L366)、[自绘节点批量绘制](../../src/canvas/tri_tile_view.gd#L43)。
- **实际问题（源码确认，未重跑像素对照）**：用斜基、三角或独立格空间时，原生 TileMapLayer 被隐藏。一张自绘 CanvasItem 统一画全部瓦片，排序时只有这个绘制对象；即使层打开 `ySort`，一个实体也不能位于同一自绘层两行瓦片之间。普通原生瓦片层的做法对此不等价。
- **最小修法**：先让自绘层的编辑面板说明这一限制，显式前后层能稳定表达已有内容。如果实际制作必须在同层穿插，再按原生可表达/不可表达分流；只给不可表达而需要遮挡的层使用可排序绘制单元，保留普通自绘层的分块路径。
- **不改的后果**：斜格等距街道、三角地形中的高物件可能在编辑器中给出错误遮挡预期；游戏侧实景预览仍可验证游戏真实画面。

### 13. 校验与写盘边界已分出一半，不过 GUI 和 MCP 仍有两套收尾

- **位置**：[正式数据检查从 GUI 反向调用 MCP](../../src/ui/playtest_controller.gd#L195)、[Workbench 发布](../../src/mcp/workbench.gd#L512)、[人工提交](../../src/project/document_commit.gd#L39)、[MCP 提交](../../src/mcp/drafts.gd#L297)。
- **实际问题**：「检查与试玩」为了跑数据校验实例化了含草稿、渲染和工具分发的 Workbench。发布虽然已共享 `preflight`，写盘、轮转、清理和结果仍分别实现；修复第 1、3 项时，若只补其中一条入口，另一条仍会报出不同结果。例如当前人工地图事务在完成写入后返回其结果，MCP 的正式写入结果还取决于是否创建了下一版草稿。
- **最小修法**：先把纯发布数据检查移到 `src/project/`，输入清单、候选地图和内容，输出问题路径；GUI 与 MCP 直接调用它。修第 3 项时把已冻结计划的逐文件写入和回执收尾收回现有 `DocumentCommit`，业务侧仍各自准备计划。保留人工确认、草稿审批、地图改名和内容暂存语义，无需全局命令系统。
- **不改的后果**：每次修校验或持久化缺陷都要追多条链，最容易漏掉的恰是大型工程依赖的批量发布和恢复。

## 可直接清理

### 14. 删除已断开的转发与重复助手

- **位置**：[资产 role](../../src/assets/asset_decl.gd#L197)、[清单 role 转发](../../src/project/manifest.gd#L282)、[未调用的画布命中转发](../../src/canvas/editor_canvas.gd#L617)、[预览旧几何助手](../../src/ui/content_preview.gd#L385)、[投影转换锚点](../../src/map/map_convert.gd#L113)。
- **实际问题**：已搜索源码、场景、测试、工具与协议文档。role 查询的两层公开方法互相调用，没有工作流使用；真实画布角标直接读声明。还有画布 `_entity_hit` 转发、`_xformed`、`ORD`、`DEFAULT_PORT` 无调用；转换复制了与 `MapViewData.anchor_unit` 相同的三分支。另有一次重复的码表失效调用（清读缓存已使码表失效）。
- **最小修法**：删除这些孤立方法和常量，用现有锚点函数；保留实际使用的角标、碰撞、坐标转换和正式测试入口。不要把只在测试或运行示例使用的函数当死代码删除。
- **不改的后果**：维护者要在多个名字相同的入口中确认哪条真在运行；以后增加锚点时两份分支可能漂移。保守可净减约 25–30 行有效/说明代码，0 个依赖；没有把搬文件算作删减。

## 架构裁决

| 范围 | 当前判断 | 决策 |
| --- | --- | --- |
| 稳定 ID、清单与游戏能力 | 地图、资产、实例、绑定与内容通过身份层级定位；字段和模块通过声明动态出现。错误多出现在不同入口对同一身份或字段的解释。 | 保留当前数据表达和游戏侧负责执行的边界。修统一解析和验证，不换 ID、不加游戏类型分支。 |
| 地图、组、网格、碰撞 | 地图和图组复用同一文档；编辑器画布使用 Godot 原生节点，再为特殊格形补绘制。格空间、层变换、碰撞与可执行对象分开是合理的。 | 保留同构文档和整组排序。只处理同值遮挡与自绘层的差异，保留图组碰撞作用域。 |
| 编辑会话、撤销与存储 | 活体画布与磁盘快照各有作用。笔刷差量、整图快照、摘要基线和 pending 回执分别解决了成本、冲突和恢复。问题是跨内容操作没都接入这些能力。 | 复用现有撤销条目和提交计划。没有必要把地图、清单、内容换为数据库，或重写画布编辑模型。 |
| 控件、面板及工作流 | 大的 UI 控制器承担不少操作，但尺寸本身没有证明存在结构问题。表单、时间轴、参照画布与游戏进程之间有真实边界。 | 只移动有明确职责冲突的代码：正式数据检查、共同写入、字段上下文。不要按大小再切出只会转发的包装类。 |
