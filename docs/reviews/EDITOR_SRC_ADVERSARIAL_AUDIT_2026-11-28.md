# 2D 游戏编辑器 · src 对抗性审查

审查基线：2026-11-28，`c8e4355f8f6d8f8bed6b08e55778cacd71dae64f`。只把 `src/` 的实现和隔离项目在本机 Godot 4.7.2 下的行为作为证据。旧审查报告未用于判定，源码未修改。

**发现 4 个建议在打包前解决的问题，以及 4 个影响明确、有独立验收条件的问题。** 前四项涉及工程重新打开、未保存编辑以及 ID 引用完整性。另有一项实测性能瓶颈、两项可从调用链直接定位的优化机会。问题集中在编辑、验证和发布之间的边界；本次没有发现需要为游戏类型或视角增加专门模块的证据。

## P1 · 建议打包前修复

### 1. 调整参考画幅后，可以保存一份下次打不开的工程清单

- **触发**：屏幕设计画幅宽 800，某元素左右锚点为 0、1，各内缩 300 像素，宽度为 200。在「项目参考画幅」内只把宽改成 500 并保存。元素的计算宽度变为 -100；界面允许这次保存，`EditorManifest.load_from()` 再打开时拒绝整份清单。
- **证据**：[`viewport_library.gd:48`](../../src/ui/viewport_library.gd#L48) 直接提交替换后的 `viewports`；[`app.gd:824`](../../src/app.gd#L824) 的通用写入口不验最终清单；[`screen_layout.gd:423`](../../src/project/screen_layout.gd#L423) 的加载校验拒绝无正面积的布局。
- **方案**：用新画幅重新算所有受影响屏幕的设计布局和对应画幅布局；保存前复用既有几何判定，指出屏幕、元素、画幅和当前计算尺寸。保留用户输入，让用户修改尺寸或先重排相关元素。没有必要自动重写布局，也不应忽略有意的局部越界。
- **验收**：800→500 被拦且磁盘摘要不变；800→700 保存且可重开；再覆盖被嵌套父级缩窄、显式画幅变体与继承基础布局三种情况。

### 2. MCP 发布会丢弃还没有保存的人工表单

- **触发**：打开「图组事件层」，新增一组但先不保存。此时让 MCP 发布另一张地图上的修改。地图工作副本没有变化，发布通过；重建工程界面时，图组编辑框被销毁，新增的组没有写入、也没有保留。屏幕、世界布局、项目内容等使用局部工作副本的表单具有相同的丢失路径。
- **证据**：[`workbench.gd:205`](../../src/mcp/workbench.gd#L205) 只看当前地图、文档操作和当前地图暂存内容；[`workbench.gd:446`](../../src/mcp/workbench.gd#L446) 发布成功后重新进入工程；[`editor_layout.gd:59`](../../src/ui/editor_layout.gd#L59) 移除旧工程界面的所有子节点；[`event_layers_dialog.gd:11`](../../src/ui/event_layers_dialog.gd#L11) 在弹窗中保存独立的清单工作副本。MCP 切工程也复用同一脏状态判断，应一起处理。
- **方案**：首先缩小刷新的范围。只发布内容或地图时，按照写入结果刷新受影响的索引和当前文档；现有表单可以保留，随后保存时继续使用已有的基线检查。必须重建工程时，先检查是否有尚待提交的人工表单。收尾时的最小补丁可以沿用现有窗口生命周期，为这些表单登记一个“待提交”的判断，不需要新增一套事务系统。预检可以照常用，真正写入和重建前必须确认可以接管会话。
- **验收**：未保存图组、屏幕布局或项目内容时发布无关改动，工作副本仍在；若只能重建，应明确阻止并且一份正式文件也没写。已保存或取消后，原请求应可正常重试。

### 3. 引用枚举漏项，删除目标后仍能保存或发布悬空 ID

- **触发 A**：A 图实体字段 `board` 为 `input/map_ref`，`friend` 为 `input/entity_ref`，以 `board` 配对，指向 B 图实体。删除 B 的实体后，人工保存前的删除检查给空结果；用 MCP 整张删除 B，`validate` 给 `valid: true`。
- **触发 B**：实体的 `choice/source: "content:logic"` 直接引用一份已有内容。内容删除的入边查询返回空，允许删除该内容。现有检查能找到功能绑定和 `flow_target`，不能找到这里的直接内容选择。
- **证据**：[`reference_index.gd:216`](../../src/project/reference_index.gd#L216) 在语义解析前用类型白名单跳过 `entity_ref` 和 `map_ref`；两者已在 [`ref_fields.gd:83`](../../src/content/ref_fields.gd#L83) 被定义为引用。[`reference_usage.gd:39`](../../src/project/reference_usage.gd#L39) 检查内容删除时只枚举 `flow_target` 和绑定。人工保存的下游见 [`map_file.gd:942`](../../src/ui/map_file.gd#L942)，MCP 验证下游见 [`workbench.gd:327`](../../src/mcp/workbench.gd#L327)。
- **方案**：引用的事实来源是字段语义，不是控件类型。让 `RefFields.describe` 决定是否为引用，再把同一份引用表交给入边查询和保存校验。内容入边按 `(功能 ID, 内容 ID)` 匹配；空间入边按地图码明确配对，再判断局部 ID。不存在的显式地图与尚未提供地图上下文应给不同结果，防止用“无法判断”掩盖已删除目标。
- **验收**：上面的跨图实例和直接内容选择都要返回带来源字段路径的提示；同批次重接或清除后可以保存或发布。覆盖默认值、数组及嵌套记录，确保同样语义不会因控件写法不同而漏检。

### 4. MCP 只按实体绑定寻找内容的本图，遗漏地图内容槽等合法入口

- **触发**：A 图的地图内容槽设置为继承本图并绑定项目内容。内容里的“本图实例”原本指向 A 的实体，随后 MCP 把字段改成不存在的 ID。全项目校验返回通过；将同一字段交给已有的空间验证器，并给它 A 图数据，立即报告实例不存在。
- **证据**：[`workbench.gd:368`](../../src/mcp/workbench.gd#L368) 仅从 `objects[].functions` 建立内容上下文，[`workbench.gd:404`](../../src/mcp/workbench.gd#L404) 找不到则传空地图，[`spatial_reference_check.gd:217`](../../src/project/spatial_reference_check.gd#L217) 对这个输入无法解析本图实例。[`map_flow.gd:38`](../../src/map/map_flow.gd#L38) 已提供继承地图的槽位枚举；[`spatial_reference_check.gd:62`](../../src/project/spatial_reference_check.gd#L62) 已有部分地图入口和内容继承遍历可复用。
- **方案**：把“内容 ID 在哪个地图上下文执行”建成一次计算。以实体绑定、继承本图的地图出口/槽和声明配对地图的入口为起点；沿明确声明继承上下文的内容跳转传播。按 `(内容键, 地图码)` 去重，避免循环。一份内容在两张地图上使用，就用两张图分别检查；确实没有约定地图的独立内容继续按无上下文处理。
- **验收**：仅靠地图槽进入的内容能检出坏字段；两张地图使用同一内容，其中一张没有目标时，错误要指向该地图；能遍历一层继承内容，并在有环时正确结束。定向内容校验与发布前校验使用同一上下文规则。

## 优化与收尾

### A. 优先优化 MCP 草稿历史的存储单位（已实测）

[`drafts.gd:22`](../../src/mcp/drafts.gd#L22) 每次从一份 JSON 读取所有历史，[`drafts.gd:75`](../../src/mcp/drafts.gd#L75) 每次编辑又把累计历史写回。对 3 万格的地图，初始草稿保存后再逐次只改一格：

| 保存的历史版本数 | 草稿文件 | 单次写入 | 再读全历史 |
|---:|---:|---:|---:|
| 1 | 约 3.1 MB | 41 ms | 28 ms |
| 6 | 约 20.1 MB | 372 ms | 184 ms |
| 12 | 约 40.2 MB | 731 ms | 319 ms |

这是本机的一次测量，表明增量修改仍需读写随历史增长的全文；不作为机器性能门槛。**建议先保留现有撤销语义，拆出头记录和单独的版本快照。** 查询与预览只读当前版本，追加只写新版本和头；列表只读头。若之后存储仍是问题，再对常见瓦片和碰撞批次做差量与定期快照。只改 JSON 缩进可以减字节，不能消除增长曲线。验收用同一张图重复单格编辑、撤销、重做和重开，当前版本的读写耗时不应随历史长度持续增长。

### B. 一次发布只建一次地图身份索引（静态确认）

[`drafts.gd:168`](../../src/mcp/drafts.gd#L168) 对每个待写地图调用 `identity_error`，而 [`map_store.gd:207`](../../src/map/map_store.gd#L207) 每次都清缓存并重新解析整套正式地图。发布 N 幅地图时，正式目录可能被完整扫描 N 次；不同于历史存储，这一项主要影响批量发布和规划。先在发布开始构造一份新鲜索引，再在计划中叠加新图、删除和改名，统一检查 ID 及目标路径。提交时保留既有的目标摘要检查。验收用批量地图计划统计读取次数，对照同一批中的重码、重名和重试。

### C. 统一正式覆盖写入的历史策略（可在现有写入口收尾）

在同一张图连续保存两版，正式文件更新，但人工地图写入没有留下 `.history/Alpha.json.1`。[`map_store.gd:245`](../../src/map/map_store.gd#L245) 直接写文件；[`drafts.gd:211`](../../src/mcp/drafts.gd#L211) 和 [`content_store.gd:189`](../../src/content/content_store.gd#L189) 则有旧版本轮转。重开工程后，人工地图与 MCP 覆盖、内容编辑的恢复能力不同。若项目希望保留“最近一次正式版本”，把已有轮转放在正式地图覆盖入口，保留作业草稿原有生命周期；无需给自动保存增加备份。验收覆盖人工保存两次、MCP 再发布一次，核对历史内容是否对应实际上一版。

## 取舍、验证范围与发布建议

- 静态检查横跨地图和图层写入、投影与格拓扑、实例与 ID、引用、图组、清单、内容与演出、MCP 草稿与发布、预览和试玩接入。隔离验证重点是上面的反例，不代表每条 UI 交互或每个游戏运行时都跑过，也无法证明不存在其他缺陷。
- 本机用隔离项目、临时脚本及独立应用数据目录复现。最终图形夹具中的 13 个判定条件全部复现，包含人工保存所调用的删除检查、正式清单重开、真实图组窗口在 MCP 发布后被清理、实际草稿截图尺寸，以及混合材质在画布节点上的归属。对照检查也确认：普通改名在目标文件已写、后续清单写入失败后，可以使用同一计划完成重试，因此未把这个候选列成缺陷。
- 未把保留越界瓦片、负视差、图组整组排序、图组碰撞作用域、投影转换保留瓦片后提示人工核对，列为本轮 bug。这些行为各有明确语义；本轮发现不要求改动原始编辑模型或新增按玩法分开的编辑面板。
- 发布顺序建议：先合并 P1 的验收用例做一次集中回归，再处理本轮 P2 中发布时明确承诺的能力。若首个正式包把大图的 AI 批量编辑作为主要用途，草稿历史优化也应进入这次收尾。最后用实际 Windows 导出包跑通过程：开工程 → 人工保存 → MCP 草稿审阅与发布 → 重开工程 → 进入游戏试玩。此次未运行完整发布矩阵，也未导出 EXE。
