# 2D 游戏编辑器：Karpathy 重构级审计

审查日期：2026-11-28。基线：`a194544`（Ponytail Ultra 修复后的源码）。范围以 `src/` 为准；游戏侧协议、现有回归和 MCP 说明用于核对契约。这次交付是审计、复现和可执行的重构方案，未改产品代码和公开协议。

## 一、裁决

编辑器的**游戏侧契约值得保留，编辑器内部的状态边界值得收紧**。通用性来自稳定 ID、清单、地图数据、实体—能力—内容，以及游戏进程拥有执行和真实画面的职责。内部整理应该让这套契约更容易维护。没有证据支持重写 ID、换存储格式、用一种渲染器包办所有格系，或为不同游戏类型拆系统。

最有回报的三处：**让地图操作按稳定身份编辑同一份数据；让正式写入共用一套已验证的提交规则；创建一次可复用的工程查询视图**。现有文件已经不少，增减文件数本身没有价值。新模块的验收标准是：它确实接管了一条状态、一项判断或一个副作用，旧路径随之消失。仅把旧函数搬家、继续透传整个 `app` 或 `canvas` 的改动不算交付。

本轮对 123 个 GDScript 做了结构扫描：40,389 个物理行，34,677 个非空且非纯注释行；扫描到 580 条显式源码路径引用边（按脚本对去重，可能包含注释或动态加载路径，不用于推断运行时调用图）。关键路径核对了 GUI 与 MCP、预览与正式文件、撤销与恢复，以及屏幕、图组、地图、演出、资产和引用之间的交界。判断以实际调用链和运行验证为准；性能数据只代表注明的夹具和路径。

| Karpathy 准则 | 本项目如何应用 |
| --- | --- |
| Think Before Coding | 先列每个动作必须保住的事实：它修改的是哪条 ID、旧数据依赖什么默认值、谁在什么时候看到改动、失败后可继续做什么。GUI 允许工作中暂时缺引用；正式发布及破坏性动作的规则应明确区分。 |
| Simplicity First | 对同一份事实保留一个所有者。已有的格何、绘制、声明、文件与预览模块优先复用；优先删除重复读写和映射，不新造全局事件总线、通用 ORM、插件框架。 |
| Surgical Changes | 一次切掉一条重复路径。保留地图和内容格式、旧图兼容、外部改动检查及正式回执。面板布局和 UI 行为无需伴随业务重构重做。 |
| Goal-Driven Execution | 每块先定可核实的前后行为：落层不变、目标不串、相同输入得到相同发布结论、失败后可重试、一个小操作不再复制全图。用既有回归覆盖相邻路径。 |

## 二、应先解决的真实差异

### A1 · 高：MCP 调整图层栈，会连带改变旧实例的图层归属

允许省略 `objects[].layer` 的地图中，摆放物默认属于第一层，这是 [MapViewData](../../src/map/map_view_data.gd#L14) 和画布的读法。MCP [图层操作](../../src/mcp/edits.gd#L189) 改顺序时不先固定旧归属，删层时又只比对原始 `row.layer`。用 A、B 两层和一个省略 `layer` 的实体实测：B 移到首位，实体从 A 变到 B；删 A 也通过，实体被留在 B。两份结果都通过地图结构校验。层配置不同时，改动会影响遮挡、变换或可见性。

**做法：** 让移动、删除使用一份与渲染相同的层语义。重排可能改变首层时，先把受影响的隐式归属明确为旧层 ID；删除先按有效层判断归属。GUI 的「确认后删层及内容」与 MCP 的「要求先移空」仍可分别保留，但共用归属、摘层和格图关联处理。图层信息改名、改顺序与移动所属实例是三件不同的事。

**验收：** 旧地图中省略层码的实体和场景摆放物重排后仍在同一层、原世界位置不变；MCP 拒绝删除它们仍占用的层；在 GUI 明确确认删除后，撤销能恢复层、摆放和格图关联。使用现有两层夹具和一条旧格式记录就可以验证。

### A2 · 高：MCP 实例码和下标冲突时，最终写入由下标决定

[实例操作](../../src/mcp/edits.gd#L256) 先按实例码查找，之后有效 `objectIndex` 会覆盖结果。MCP 查询又会返回带码对象的下标。实测两例 M001、M002，把 M001 和指向 M002 的下标一起送给删除操作，返回成功，最后只剩 M001。引用检查保护不了一个没有来向引用的正确实体。

**做法：** 传了实例码就按码查找；同时传了下标则核对是否指向同一行，有冲突即报错。只传下标按说明用于无实例码的场景摆放物。也修订查询/操作文档，说明下标随草稿版本和批内改动变化。实体定位继续靠原有 ID，无需给场景装饰强制发执行码。

**验收：** 匹配的两个定位符可以编辑；冲突和已失效的实例码不会修改任何一行；仅下标仍可编辑无执行码的摆放物。对新增、修改、删除分别检查目标行及批次失败时的状态。

### A3 · 中：正式内容的语义校验分入口

MCP 发布走 [ProjectDataCheck](../../src/project/project_data_check.gd#L121)，其中调用 `ContentValues.check`。GUI 的[绑定内容](../../src/ui/content_form.gd#L605)、[内容库保存](../../src/ui/project_content_library.gd#L780)和[暂存内容提交](../../src/project/document_commit.gd#L7)不经过相同的值检查。定向验证：声明为整数的字段在正式内容文件中写成字符串，`write_ex` 成功，`read_ex` 返回 `ok`，值校验明确拒绝。正常表单通常已约束类型；实际差异在于打开清单变更前的旧内容或外部修改后的内容时，只改标题、其他字段或演出，就可能保留并再次写出不合当前声明的数据。没有观察到表单能直接输入这个错误类型。

**做法：** 底层仓库仍负责解析、摘要与写文件；不要让旧文件因声明不匹配而失去打开和修复入口。把值检查接到各自的正式写入决策。对即时编辑，拒绝本次新增的错误，暴露原有错误及可修复字段，避免用户需要同时修完所有旧字段才可操作；对显式发布/验收，阻断新提交的错误数据，报告未涉及的历史数据并允许进入修复。引用跨地图的判断使用实际候选工程，不在单一字段组件里重做全项目校验。未知扩展键依然保留。

**验收：** 同一个非法演出步骤或字段，在项目内容库、绑定内容和 MCP 检查中得到同一处错误定位。正式提交不能新增该错误；已损坏的旧内容可以打开和逐项修正，修复后的文件通过检查，未知键往返不变。

## 三、可落地的重构

### B1 · 优先：从 `map_of` 移除每条 MCP 指令的整图深复制

[MCP apply](../../src/mcp/edits.gd#L23) 在入口浅复制索引供后续差量落盘；[每条地图操作](../../src/mcp/edits.gd#L147)又走[草稿读图](../../src/mcp/drafts.gd#L258)，已在本批次改过的地图仍执行 `duplicate(true)`。当前磁盘正文复用已经解决了版本写盘膨胀，这个不同的问题发生在编辑一批指令时。用同一个 map.patch 连续改 60 次出生点，四次结果：空图 0.353–0.367 ms；6 万瓦片 765.417–972.955 ms。只测操作循环，不含 HTTP、初次读取、最终校验、写盘或渲染。源码给出的复杂度是「操作条数 × 整图大小」。

**改法：** 进入批次的时候把当前批次当作独占的修改范围；首次写某个地图/内容时复制它，后续操作直接使用该批次的可写副本。保留变更前索引供正文复用。把只读的 `map_of` 与批内专用的取可写记录分开；不要在其他调用点突然改变 `map_of` 的复制语义。最后一条失败，丢弃这批副本，草稿和重做历史仍停在上版。先处理地图，内容验证确实共享同一机制后再复用。任何时候最多一个批次拥有可写版本。

**验收：** 6 万格夹具 60 次同图 patch 只复制一次，60 次修改只写一次新的地图正文；最后一条失败不变更正文、版本或 redo；同一批读到前一条指令的结果。主要比复制次数和规模曲线，计时只作旁证。

### B2 · 优先：统一正式文件计划，保留 GUI 与 MCP 的会话差异

[DocumentCommit](../../src/project/document_commit.gd#L39) 已共用 preflight、写入循环、回执底层，但 GUI 还在计划中保存原字典和内容行，由回调重新选择存储器、编码和校验；MCP 另一端在 [drafts.plan](../../src/mcp/drafts.gd#L304) 先冻结文本，并在 [通用 writer](../../src/project/document_commit.gd#L104) 写。这使「用来算写后摘要的内容」「最终写入内容」「失败后如何确认已写」需要跨两条链检查。GUI 地图保存、复制/投影转换、首次保存时改名、图组绘制与 MCP 发布也分别编排清单和副本生命周期。

**改法：** 聚合到一个小的正式写入入口：每个条目描述目标、原始状态或摘要、写入文本或删除，以及需要保留的文件历史。由它做冲突检查、单文件替换、回执和后续重试；不同入口仍负责确认、形成候选、业务检查和成功后的界面刷新。优先迁移「GUI 保存地图及其暂存内容」和「MCP 发布已冻结内容」；能复用时再接入复制或改名。一般只需现有计划条目加文本，无需设计一个通用事务语言。清单序列化剥离内部键应移出 `app.gd`，GUI、MCP、预览统一调用。仅大小写改名在 Windows 是独立文件操作，用现有分支并纳入同一基线/历史契约，确认时不改其公开行为。

**保留理由：** 多个文件独立发布，进程中断后可能剩下一部分已经写入，现有回执确有作用。也不能把「正式文件已写成功，清理失败」改回「发布失败」。安全收益来自写入与恢复事实一致，不来自再包一层异常处理。

**验收：** 对同一候选数据，从两个入口写出等价文件，回执预期摘要等于最终文件摘要。保留既有的占用冲突、已写一条后失败、重开后继续、拒绝覆盖外部改动和发布成功后草稿清理失败的用例；另外覆盖一次只改大小写的 Windows 改名。

### B3 · 优先：查询一次实际工程状态，引用遍历复用结果

[ProjectDataCheck](../../src/project/project_data_check.gd#L18) 依次取地图索引、地图正文、绑定和内容、上下文、引用、屏幕与流程目标；同一内容被多个实例使用时会多次调用 [ContentStore.read_ex](../../src/content/content_store.gd#L111)。内容缓存命中前仍读全文并计算摘要，命中后还会复制。反查、删除预检和配对地图检查在 [ReferenceUsage](../../src/project/reference_usage.gd#L308)、[SpatialReferenceCheck](../../src/project/spatial_reference_check.gd#L109) 与各面板另走遍历。[MapStore](../../src/map/map_store.gd#L144) 对整个 manifest 求哈希，包括放在其中的草稿叠加，文件索引与声明状态绑得过宽。这些是代码成本证据，尚未测得真实工程中各段耗时比例。

**改法：** 第一步只在一次显式校验/反查中复用按 `(功能 ID, 内容 ID)` 的读取结果，包括不可读状态。复用现有 [RefFields](../../src/content/ref_fields.gd#L68) 和引用收集，不另写一套分析器。第二步在测出重复确实来自跨操作时，再把正式数据、当前画布和草稿叠加表示为一个只读工程视图：查 ID 时使用该视图，MCP 查询和 GUI 候选共用规则；识别不到的源明确标记，浏览可以读缓存，发布和删除用最新扫描或受摘要保护的读结果。声明更新用自己的版本，避免内容保存导致所有声明重算。配对内容的循环继续按「内容和地图」去重，不能只按内容去重。

**验收：** 用一百张地图、一千个实例，其中五百条绑定指向同一个内容，检查一次校验读取其正文一次；报告的来向、配对地图、缺失和不可读信息不变。再验证切图、外部修改、叠加草稿和删除，工作视图不会混读旧版本。只为测出的跨操作瓶颈引入长期索引，不给整个工程增加后台常驻索引服务。

### B4 · 优先拆职责：画布、手势、撤销与序列化

[EditorCanvas](../../src/canvas/editor_canvas.gd#L245) 既保有地图元数据，又从 Godot 节点读取已放置实例和瓦片。[_restore_placement、_object_row、extract](../../src/core/undo_history.gd#L601) 放在撤销里，载入与保存也依赖撤销模块。[图层操作](../../src/canvas/layer_ops.gd#L182) 改排序等元数据前要提取整图，再重建渲染树；[extract](../../src/canvas/editor_canvas.gd#L1743) 甚至要根据是否只读来取消或拒绝读取当前预览手势。脚本物理上分开，输入和绘制脚本各直接用到约 87 个不同的 `cvs` 成员，`selection_ops` 约 69 个。说明拆文件没有划清状态边界。

**改法：**

1. 先定一份实例记录与地图快照的转换接口，把现有编码搬出撤销，让加载、保存、地图复制、撤销共用；迁移时保持原样往返，包括未知资产、扩展字段、层码、坐标精度。只依赖快照/对象容器和格系的转换留下来，UI 属性不进入它。
2. 第一条真实命令选「图层重排」：输入稳定层码和目标位置，产出小的顺序差量，与 A1 同一块实现。画布以层 ID 调整已有显示容器，只同步需要变的索引、遮挡和选中层；只在投影、格系或整体加载确实变化时重建。瓦片笔刷的现有差量继续用，暂不为所有操作引入命令基类。
3. 再把实体拖动的临时位置作为手势状态，松手才应用持久写入；绘制读预览，保存和查询读已确认数据。待实例、层操作证明边界可用之后，再考虑能否以文档记录作为更多操作的权威数据。保留 TileMapLayer 对普通地图的优势，不先复制一套完整场景到内存。

**验收：** 对比加载—保存与撤销—重做的有效数据；重排不重建每个实例或瓦片；拖动时只读查询无副作用，取消拖动不产生编辑，完成只生成一次历史。用普通正交、自绘三角、格图边和带变换的层分别验证。不要仅用「画布文件缩短」验收。

### B5 · 演出和内容：让一次编辑的状态走一条路径

[StepsPanel](../../src/ui/steps_panel.gd#L703) 读取工作副本时顺便更新写回摘要；修改步骤后会重读文件，并协调表单、分页显示和时间轴的多份数组快照。[项目内容库](../../src/ui/project_content_library.gd#L755) 又有独立提交流程。大部分检查在保护真实风险：多个内容窗口或切换绑定后不能让旧回调写错数据。复杂度来自同一编辑同时靠数组相等、下标、结构版本、绑定对象身份和文件摘要表达。

**改法：** 先建立一个明确的、属于「当前内容编辑」的值：内容身份、读取摘要、内容数据与当前结构版本。面板操作只提交「针对这个版本的指定步骤补丁」，用现有 `StepTimeline` 完成修改。一次成功写入返回可继续编辑的内容及摘要；列表、详情和时间轴从这份结果刷新，减少手动对三份快照作补丁。继续保留外部摘要比对、独立预览、内容未绑定之前不发 ID 的行为。绑到实例的编辑和项目内容库仍可采用各自的提交时机；共用值检查与仓库规则即可。第一轮无需为每条步骤新增磁盘 ID；若将来要跨任意重排及跨会话精确追踪同种步骤，那才是协议需求。

**验收：** 连续修改 200 步演出的同一步不会卡焦点；拖动一次仅写/记一次历史；外部改动、过期选中、切换绑定、暂存到落盘、撤销和重做各验一次。检查读取次数下降，并确保游戏实机预览仍取到多演员当前内容。

### B6 · 预览与试玩：复用请求装配，避免过重的世界快照

隔离的 [GamePreview](../../src/project/game_preview.gd#L54) 进程是合理边界。GUI 有 [MapGamePreview](../../src/ui/map_game_preview.gd#L320) 和时间轴请求装配，MCP 的 [media.render](../../src/mcp/media.gd#L212) 也采集地图、画幅、相机、暂存内容、演员绑定和时间。目前的区别有两种：GUI/MCP 要从不同工作副本读文件属于必要区别；同一预览能力如何算取样时间、选择演员和发送同一项数据，没有必要各自解释。另一个确定的放大点是：MCP 世界预览对每张被改地图挂一份全部暂存内容，再整体 JSON 编码。若 20 张地图和 240 KiB 暂存内容，即使忽略地图本身，重复数据也已超过 4 MiB。这里依据格式和上限推算，未跑 20 张图的实际渲染。

**改法：** 从重复最多的一种能力开始，共用纯请求构建器，GUI 提供当前工作副本、MCP 提供草稿视图；上层仍拥有窗体、截图和取消。世界协议可考虑追加一次共享的内容叠加，让明确声明支持的游戏只读一份；旧 `{map, stagedContent}` 请求保持原义。等剖析确认这条路径是限制后再改兼容协议。时间轴非时间字段更新、取帧批处理、独立预览进程均以实际耗时为依据，无需为少量取样常驻游戏进程。

**验收：** 对同一地图、演员、相机和取样时刻，两入口交给游戏的参数等价；排除重复内容后世界快照大小与内容条数成正比；旧夹具仍按原请求工作，失败和取消仍能从独立进程退出。MCP 截取编辑器本身仍归 UI 截图链。
