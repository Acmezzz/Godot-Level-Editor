# 2D 游戏编辑器：真实制作、试玩与易用性实测

测试日期：2026 年 11 月 28 日。被测源码：`1bd6ab6`。环境：Windows、Godot 4.7.2、OpenGL Compatibility；编辑器窗口 1280 × 800，试制游戏 800 × 480。

**结论：三个差异明显的玩法切片都做出来并实际玩通了。** 横版机关演出、等距行动点解谜和六边运输用的是同一版编辑器。没有为任何一种玩法新增编辑器代码、专用面板或专用编辑协议。新手能从空地图走到「摆实体、配对白、试玩看到结果」；目前主要障碍是找入口和确认状态。最值得先修的是：**试玩保存成功后仍显示「未保存」，以及 MCP 写入了无效时机却通过校验。**

## 一、实际做出了什么

制作走两条独立路线：复杂原型经正在运行的原生编辑器 MCP 创建草稿、校验、截图、发布，再由独立游戏进程加载正式文件；首用体验从另一个空工程开始，用鼠标和键盘在原生界面操作。游戏夹具提供移动、相机、玩法、绘制和执行逻辑；地图、图组、节点、边、屏幕、对白和时间表均由编辑器写入。测试项目和应用配置与工作工程隔离。

| 制作样例 | 编辑器交付的内容 | 试玩观测 |
| --- | --- | --- |
| 横版信标回廊 | 正交地图、同图三角格警戒带、普通碰撞、三个整组排序的图组、负/正视差、无贴图信标绑定和固定状态条实例 | 普通地图墙阻挡一次，通过只画在前景图组中的墙；这是夹具分别选择两种碰撞数据的结果。相机 X 从 64 移到 96，HUD 仍在 `[18, 36]`。图组排序读到 `[-2, 0, 2, 5]`；三套视差值 `0.25`、`-0.5`、`1.35` 参与运行绘制。 |
| 等距行动点解谜 | 等距底图、异形区域、有向边、边的成本和解锁字段；复用横版的一组远景和「进入地图」事件 | 演出按内容 ID 跳入等距地图。只保留适用的图组 `[-2, 0]`。以 3 点行动力开始，提前选出口被拒绝，在开关和出口各扣 1 点，最终余 1 点。 |
| 六边物流 | 六边底图、四个异形节点、有向边、运费、矿点载货字段 | 空载走捷径被拒绝；矿点取 3、枢纽剩 2、港口剩 0，交付计数为 1。与等距关共用格子图和字段机制，差异在游戏侧规则。 |
| 标题与音量设置 | 启动画面、两个屏幕的文本和按钮、锚点、内容 ID 跳转、调音量模块 | 从项目入口实际打开标题屏，鼠标点「设置」进入第二屏，点按钮后音量变为 25%；键盘返回并进入横版。另单独用屏幕入口启动设置页，不经过标题屏。 |

横版演出专门做了一个容易把工具推到极限的例子：**29 步、7 轨，控制 25 个初始隐藏图层。** 信标触发同一条内容，先并行出对白、播音频、亮警报带，再启动 24 层扫光，淡出后执行跳图。运行断言捕获到至少 7 个图层同时亮、首层熄灭后尾层仍亮、转场前 25 层全部熄灭；图层由 ID 定位，跨视角凭内容 ID 接续。另通过 MCP 成功抽取 WAV 片段，并在游戏进程中观测到音频播放器正在播放。

这组试验检验的是编辑器能否把游戏模块编排成运行内容。相机跟随和 HUD 屏幕定位由夹具实现；图组本身只保存复用对象、顺序和事件。测试对白是一段有时长的字幕；视效是显示/隐藏和淡变，夹具用色块标明 `blend: add`，不以此证明实际材质的加色效果。音量档位已观测，未做混音听测或节拍对齐。更复杂的分支对白、不同画幅的焦点与重排、逐帧角色动画、物理或联网玩法、超大地图性能和导出后的 EXE 均未据此判定通过。

## 二、从人的角度走一遍

这是一次以新手任务为目标的操作走查，不计入真实受试者学习速度或无障碍合规结论。

| 新手任务 | 实际结果与卡点 |
| --- | --- |
| 打开项目、建第一张地图 | 首屏有明确入口。误选 `maps` 文件夹时提示缺失文件路径，能重选；提示先说「选择游戏工程根目录」会更好懂。空地图有创建按钮，漏填名字后可修正。新建窗口同时出现投影、拓扑、基向量，第一步要理解的概念偏多。 |
| 铺地面、摆实体、改错 | 实际画下瓦片，用 Ctrl+Z 撤销、Ctrl+Y 重做。放置信标后自动选中，画布的「在工作台编辑」把人直接带到该实例。资产页能看图和尺寸，也能看到「在地图上使用」入口；未验证该入口的完整跳转。 |
| 给信标加对白并试玩 | 从绑定行选「交互」，打开演出，填写对白与 2.5 秒时长，切到时间轴，Esc 返回，试玩实际显示输入的文本。功能名看起来像静态文本，移动鼠标上去才发现能展开。「SAY0」出现在内容摘要里，第一次使用的人更容易理解「显示对白」。 |
| 给多张地图共用同一套绘制和事件 | 用地图下拉新建图组、选适用地图、排到普通图下面并打开绘制。这个入口看不到「进入地图」；要从内容 → 项目内容库 → 图组事件打开另一个版本的同一窗口。已在 GUI 找到事件入口，运行通过的是 MCP 写入的事件。 |
| 排一个菜单按钮 | 用内容 → 参考视图 → 编辑屏幕布局，拖矩形、输入 `Resume` 并保存 `practice-menu`。摆放和选中有效；要先猜到「参考视图」也能做菜单，而且页脚仍写「保存参考视图」。这张手工界面只验证到保存，实际可点按钮由上面的标题和设置样例证明。 |
| 给世界加一个分块 | 用地图下拉打开世界布局，把普通地图加入并保存。地图下拉中能识别图组绘制文档，但世界布局下拉又把它当普通候选，示例里还排在第一项，容易选错。 |

目前最适合延续的交互是「摆好后直接去配这个实例，再直接试玩」。其他入口也可以按同一原则整理：用户从一个对象出发就能找到相关的编辑动作，保存后能确认结果。现有面板已能覆盖这些任务。

## 三、应修的实测问题

### P1：实例绑定填错触发时机，MCP 校验仍通过

正式样例用声明的执行码 `USE0`，实体按键后正常执行。随后在副本草稿把同一绑定改为声明 ID `interact`，`binding.put` 接受，`validate` 仍返回 `valid: true`，没有触发时机诊断。界面曾以「当前值」显示 `interact`；游戏按规范读 `USE0` 时不会识别这个绑定。反例草稿未发布。

根因是 [MCP 绑定写入](../../src/mcp/edits.gd#L307)直接复制字段，[地图验证](../../src/map/map_data_validation.gd#L320)只检查 `trigger` 是字符串；[界面候选](../../src/ui/fn_bind.gd#L305)则从功能允许的触发声明取执行码。建议把「此功能可用的执行码」做成共用查询：MCP 入口明确接受哪个标识，给错时列出可用值；草稿验证同时检查已保存的非空值，空值保持默认时机的语义。如选择也接收声明 ID，先定清楚同字符串可指向两个声明时怎么处理，写盘仍只保留执行码。验收要同时覆盖正确码、未知码、声明存在但此功能未开放的码，以及默认时机。

### P2：试玩已经自动保存，画布仍显示「未保存」

鼠标编辑地图后直接点「试玩地图」，游戏显示刚输入的对白。退出后左下角回执显示游戏已加载本次数据，右下角仍亮着「未保存」。正式地图文件已有本次画下的 `[3,3,"floor",0,0,0]`。这是状态误报，未观察到数据丢失。

[保存收尾](../../src/ui/map_file.gd#L1049)清掉 `modified_flag`，[界面更新](../../src/ui/editor_layout.gd#L611)却从置脏等路径主动刷新。让成功保存统一更新地图标题与徽章，失败时保留原状态。验收：Ctrl+S 与试玩触发的自动保存成功后都立即熄灭徽章，新的编辑操作再把它点亮。

### P2：按指定时间打开演出，光标与下方读数不同步

同轮短版演出截图中，MCP 请求定位到 `0.55s` 后红线停在 `0.55s`，下方却还是「播放头 0 s → 0.000 s」，参考音频位置也显示零。[打开时间轴](../../src/ui/steps_panel.gd#L182)直接改画线位置；[已有定位方法](../../src/ui/steps_panel.gd#L957)还会刷新读数与帧预览。建议复用同一定位入口，并保留布局完成后再滚动到光标的时机。验收：同一个非零位置下，光标、时间读数和预览索引一致；秒、帧和拍三种时间单位各抽一例。

## 四、值得做的通用优化

| 优先级 | 观察 | 建议与验收 |
| --- | --- | --- |
| 高 | 演出 4 条扫光轨需要重叠，正确结果却生成 48 条成对提示（12 条列出，其余折成一条提示）；提示占去大幅窗口空间，时间轴上重叠的短块也难以点选。 | 轨道旁显示「重叠次数」并按需展开，诊断区不挤按钮和读数；列表和时间轴互相定位，让相互覆盖的短块可以选到。保留可执行的同轨重叠；如果将来清单真能说明动作争用同一目标，再把冲突和正常并行区别显示。 |
| 高 | 图组的绘制与事件分散在两处；菜单和设置界面的入口叫「参考视图」。 | 地图与内容工作区用同一个「图组」窗口，分别预选绘制或事件区域，并能看到或切到另一部分。内容首页加面向任务的「屏幕界面」入口，打开现有面板并默认到布局，继续保留参考图热点用法。用户从地图能找到某个图组的进入事件，从内容能找到主菜单布局。 |
| 中 | 地图新建的高级参数太早出现，功能名可展开但没有显著提示。 | 首屏保留名字、尺寸和带小示意的投影选择，拓扑、轴向和基向量放到「高级」。功能行加统一展开标记，摘要用模块显示名，执行码放辅助信息。让简单地图与第一条对白可以在不理解全部术语时完成。 |
| 中 | 扫光和连续揭图能编排，逐个改 24 步的间隔或改成更大的扫光成本高。 | 先实现时间轴多选、共同平移、按间隔分布，以及选中步骤到图层面板的 ID 定位。继续使用现有步骤和图层引用。同一套操作也可调整连续字幕、声效、触发与可见性。 |
| 中 | 世界布局候选未标识图组文档。 | 复用地图导航对图组绘制文档的标签，分到独立分区；普通地图在前。已存在的合法世界分块仍能定位。 |
| 低 | 接入试验曾用旧夹具的 `cell: 16` 配 16 × 16 图集；当地图格宽改成 32 后切片不可用，界面没有把错指向 `assets.*.cell`。按规范用 `cell: {w: 16, h: 16}` 后通过。 | 先把明确写错的 `cell` 类型和有效切片尺寸大于图片的错误定位到资产字段，保留省略该字段时的已有默认值。让接入者在工程诊断里就能找到资产和正确格式。 |

功能行右侧的窄窗可达性值得用同一轮改动回归：1280px 截图只完整显示到排序箭头，后面还有操作，尚未核实 Tab 或调整窗口能否触达，故本轮不立为已确认缺陷。

## 五、能力边界与复跑

三个切片证明同一套资源、图层、图组、实例、字段、格子图和 ID 可以组合不同玩法。以后衡量表达上限，可优先选三条差异更大的任务：节奏演出验证拍点与试玩采样是否一致；实时潜行验证路径、区域、状态切换在画布上是否容易看懂；多画幅设置验证布局、焦点和返回路径。若卡住，应先定位是游戏侧没提供执行模块、编辑器缺一种通用输入/引用/编排方式，还是内容能做但难找或难观察。按这个边界补能力，不必增加按品类划分的编辑模块。

自动部分从仓库根目录执行：

```powershell
node tools/experience_live/run.js tools/shots/live-authoring-20261128/final
```

用 Windows 桌面会话、Node.js 24（实测 24.18.0）、Godot 和装有 Pillow、pywin32 的 Python。脚本默认使用本机路径，可用 `BIRD_GODOT`、`BIRD_PYTHON` 覆盖。测试会前置自己的试玩窗口并发送鼠标、键盘输入。`workspace.json` 提供一次性项目路径；其中 `fresh` 是空白手工走查项目。实测最终命令退出码为 0，自动记录的 `issues` 为空；补验开始时曾有一次 Godot 资源导入进程以 `0xC0000005` 退出，后续完整运行成功，未定位为编辑器代码缺陷。

本机证据在 `tools/shots/live-authoring-20261128/`，为开发期产物。`final/runtime-results.json` 是运行断言的观测值；`final/validation.json` 是正式样例校验，`final/invalid-trigger-validation.json` 是未发布的反例。`final/author-timeline.png`、`final/play-04b-layer-pulse.png` 分别为大量重叠的编辑画面和实际扫光；`ux-23-gui-play.png`、`ux-24-play-receipt.png` 为手工对白和未保存状态误报；`ux-26-groups.png`、`ux-35-group-event.png` 与 `ux-33-screen-properties.png` 为两种图组入口和屏幕布局。根目录同名 `author-timeline.png` 是短版播放头读数反例。精选证据可在本机同目录的 `experience-evidence.zip` 查阅。
