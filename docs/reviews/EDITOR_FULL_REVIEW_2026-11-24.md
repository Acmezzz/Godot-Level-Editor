## 1. 结论与发布口径

编辑器已经有一条完整的常规制作链：游戏侧声明资产、功能、条件、时机和步骤；编辑器制作地图，挂载功能并填写内容；游戏侧读取数据、决定行为。图层、格空间、引用字段、时间轴、身份和恢复都有可用实现。这条分工正确，应保留。没有证据表明应换编辑器框架或将游戏运行时代码引进编辑器进程。

**可以作为“声明驱动的通用 2D 地图与实例内容编辑器”交付试用；还不能按“接入成品模块后，任意 2D 游戏都能在编辑器内完成内容开发”验收。** 两者区别在于：能存某段 JSON、能下拉引用游戏侧生产的数据、能独立在编辑器里制作并验收这段内容，是三层能力。当前常规格图和实体挂载已到第三层，非规则空间、多画幅、可复用全局文档和外部模拟主要停在前两层。差距是少数横向基础能力，并不等于要逐个游戏类型添加专用工具。

同时不建议把当前工作区当作稳定格式基线发布。最先解决的是：复制/转换的写盘依赖、内容删除漏查、格边数据源分裂、三角/六边区域操作。P1 表示普通制作路径有实际错误或可写出失联数据；P2 表示限定工作流下错误、规范缺陷或显著维护成本；P3 表示值得排期的优化。场景需要故障注入或 UI 观察的地方注明为待验，未将其当成已实测结果。

## 2. 数据完整性与编辑正确性

### P1-01　整图复制和转换未按依赖顺序保存清单；转换还漏传暂存内容

- 证据：[普通复制](../../src/ui/map_file.gd#L283) 用 `copy_content_source()` 收集工作副本和暂存行；[转换入口](../../src/ui/map_file.gd#L171) 提前提取地图，应用时只传转换后的文档（[写入调用](../../src/ui/map_file.gd#L249)）。[MapStore.duplicate_map](../../src/map/map_store.gd#L440) 的冻结目标只有新内容和地图；[常规提交](../../src/project/document_commit.gd#L24) 才会排清单在首位。
- 影响：新绑定刚填写但未保存，转换会按缺失内容失败；首次接入后补发功能码或扫描新资产，普通复制可以把只有内存清单能解释的绑定写进正式文件。此时关掉编辑器或换进程试玩，磁盘清单不能解释副本。转换预览和最终提交也没有共享源快照与文档修订凭据。
- 方案：两个入口共用“冻结源文档 → 纯变换 → ClonePlan → 目标提交”流程；冻结包括 `(generation, revision)`、清单有效载荷、地图、复合键暂存内容；先验证全套目标，再按清单、内容、地图顺序写。保留源地图不写的行为。验收：首次补码 + 新建内容时两种另存均可在重启后被读取；清单冲突时两个副本目标都未写；源修订变化时须重做预览。

### P1-02　删除正式内容时漏掉暂存间接引用

- 证据：[删除前检查](../../src/ui/content_form.gd#L1562) 对暂存内容只看顶层 `fields` 的字符串是否恰好等于 ID。正式内容走 [ReferenceIndex](../../src/project/reference_index.gd#L63) 和 [审计的字段递归](../../src/project/project_audit.gd#L556)，范围包括步骤、结构化行、多选。暂存没有沿用这条路径。顶层循环也不区分引用字段、普通字符串或目标功能。
- 影响：尚未落盘的关卡内容在步骤、多选或行记录里引用目标时，可能删掉仍在使用的正式内容，随后保存得到悬空引用；非引用文本刚好等于 ID 又会误拦。
- 方案：从功能、条件及步骤声明构建一份递归引用遍历器，输入源文档与源身份、输出目标 `ContentKey(fn_id,cid)` 和字段路径。正式、暂存、草稿、删除、审计、关系图均使用该结果；读不完整时不执行删除。验收：步骤、多选、嵌套与跨功能同 ID；同时验证普通文本不拦删除。

### P1-03　格边下拉读取旧瓦片，点选和自检使用不同规则

- 证据：[活画布候选](../../src/canvas/editor_canvas.gd#L1060) 实际将 `map_data` 交给 [edge_candidates_of](../../src/content/ref_fields.gd#L234)，并未读取当前格存储。笔刷写节点，[_save_now](../../src/ui/map_file.gd#L1034) 保存后也只回写了 `map_data.meta`。下拉要求两端都有瓦片，但不筛范围；[画布命中](../../src/canvas/editor_canvas.gd#L983) 只查邻接与距离；[自检](../../src/project/project_audit.gd#L911) 查边值、范围和邻接，不查占用。
- 影响：新涂两格下拉不刷新，擦掉的边仍在列表；外边界可能点选后被审计判无效。格边制作无法用一种口径复现。
- 方案：把 `edge_ref` 定义为“目标图内规范共边”，占用作为可选声明过滤器（如 `occupancy: both`、可指定层），或明确所有入口均要求占用。做一个接受 live/disk 快照的 `EdgeQuery`，共用规范化、范围、过滤、几何和诊断。活体缓存以地图片段修订为键，不以整图重开为更新条件。

### P1-04　六边与三角区域复制/移动的相对坐标不是同一套几何

- 证据：[copy_region](../../src/canvas/region_ops.gd#L249) 用整数格号相减生成瓦片/碰撞偏移，[粘贴](../../src/canvas/region_ops.gd#L357) 把偏移当作原点格号再调用 `shift_cell`。该函数在 [GridSpace](../../src/canvas/grid_space.gd#L378) 中按像素平移后重拾取；六边 odd-r 行相减不具平移不变性。三角奇数列位移会切换三角朝向，任意半列平移会跨过交替的对角线。实体模板则以连续坐标相减、相加（[模板](../../src/canvas/region_ops.gd#L115)、[落位](../../src/canvas/region_ops.gd#L211)）。
- 影响：六边区域即使粘回原选区起点，跨奇偶行时也可能横错一列；挪奇数行时移动后的格集合未必仍等于移动后的矩形选择。三角的奇半列操作可能让瓦片朝向与原构图不一致。当前先清旧格再写新格，目的地覆盖、越界和源目标拓扑不兼容没有一个完整的落笔前计划。
- 方案：六边用 axial 坐标存相对格位并做整数对账；三角定义保朝向的平移群，奇列操作要拒绝、吸附或要求显式重采样；实体采用相同世界位移或明确独立锚点策略。计划列出原格、目标格、层映射、覆盖、越界及引用影响后一次应用。验收：奇/偶来源与目的地、原地粘贴、逆向移动、混合瓦片/碰撞/实体、变换层，并验证源数据和撤销逐格一致。

### P1-05　重复身份未全部在“校验 → 注入 → 补发 → 写盘”链上封闭

- 证据：[清单加载](../../src/project/manifest.gd#L67) 先校验，后注入内置资产、随机补实体码，再扫描；随机补发实体码的循环没有占用表，也没有最终校验。内置 `trigger_zone` 固定 `TZ99`（[内置声明](../../src/assets/builtin_kinds.gd#L15)），故手写实体可先用该码通过校验，合并后出现两条。保存又剥掉内置条目。地图写入 [MapStore](../../src/map/map_store.gd#L253) 做单图校验，项目撞码另在索引/审计处理。
- 影响：临时或正式引用的身份不可唯一解析；项目复制、查看草稿和跨图跳转尤其依赖地图码唯一。没有碰撞不代表分配器有唯一性保证。
- 方案：所有代码统一由分域分配器处理，先加载占用表并预留内置键，再补码，最终校验实际会参与编辑的清单；地图写计划对该项目索引施加唯一性约束，改名允许预期的旧键到新键替换。对旧重复码提供迁移预览和引用更新，不能静默改发。

### P2-01　未落盘改名与正常保存对暂存的取舍不一致

[首次改名](../../src/ui/map_file.gd#L541) 会在收集字段前独立保存清单，之后把当前文档所有暂存行当成新建目标；没有沿用 [常规计划的绑定依赖判定](../../src/project/document_commit.gd#L24)，也没有保留替换基线。若新建内容绑定已被撤销，普通提交会丢弃无绑定的暂存，首次改名却可能写出孤儿。对恢复草稿带替换基线的条目，也会按创建目标处理。让两条入口复用同一个“当前地图依赖集合 + 恢复基线 + 暂存去留”的规划器，测试撤销后首次改名与创建/替换两类草稿。

### P2-02　提交日志能诊断部分成功，尚不是可操作的恢复事务

[改名](../../src/map/map_store.gd#L385) 是先创建新 JSON 再删旧文件；后一步失败可留两份同码图，[日志读取](../../src/map/recovery.gd#L327) 依据摘要分类，[启动处理](../../src/app.gd#L214) 展示恢复信息。普通提交在首个正式目标之前调用 `commit_fields()`，已有内容仍可通过 [表单即时写盘](../../src/ui/content_form.gd#L495)，所以“取消/失败任何文件不写”不能覆盖所有控件回调。另有“比对摘要后再替换”的外部并发窗口；同目录临时文件替换不等于跨文件原子，也不等于掉电耐久保证。

建议保留现有可判读日志；增加可预览的定向前滚/回退，改名旧文件未删除时明确列两图和同码冲突，给“确认保留新版”“撤销新文件”两种操作。编辑器内多实例用项目写锁；外部写入方仍按摘要复验报告冲突。将已有内容即时发布与统一提交的边界写进文档；若作者要求“失焦不落盘、丢弃能还原”，将其纳入同一工作副本。验收用目标写成功、后续删除失败及进程中断三类故障注入。

### P2-03　裁剪、投影转换与引用的后置完整性不足

[裁剪](../../src/ui/map_dialogs.gd#L101) 统计并删除瓦片、碰撞、摆放物，不检查出生点和存活引用；[地图校验](../../src/map/map_data_validation.gd#L102) 接受两项数字作为 spawn，[载图](../../src/canvas/editor_canvas.gd#L456) 转成整数。缩图可让出生点、格边及实体引用留在旧边界；转换还会把连续坐标量化到 0.001，再将出生点按目标格拾取（[MapConvert](../../src/map/map_convert.gd#L24)）。转换的格边计数仅扫摆放物 props、按字典有 `edge` 键判断，未按声明遍历内容/步骤/行，也未对跨图边排除。不要承诺像素严格不变。

建议对这类命令先生成影响清单：新边界外出生点、被裁对象和入边、目标拓扑无法解析的格边、只读格图不随地图缩放的风险；给迁移、重选、保留待修或取消选项。出生点的契约应显式要求整数格号，并区分允许的编辑临时值与正式发布规则。

### P2-04　图层混合、格形和预览是不同渲染器，能力未完整对齐

- [画布层装配](../../src/canvas/editor_canvas.gd#L314) 对原生瓦片与实体使用分段容器，对三角及斜基使用自绘节点；混合材质只设给 `below/ysp/tn/above`，没有设置给自绘瓦片或实体画项，也无贯通的父材质继承设置。配置接受 `add/mul`，但不能把这些分支宣传成同一视觉效果。自绘格的瓦片是一个节点，逐瓦片与实体 Y 交错不可用。
- [内容预览](../../src/ui/content_preview.gd#L188) 自绘，实体只画四边形/缩略图，没走 poly/path；[瓦片](../../src/ui/content_preview.gd#L323) 按格多边形铺 UV，可能与原生层的超格切片外观不同。取景的 [scene_bounds](../../src/map/map_view_data.gd#L78) 合并名义格边界及各层变换，并未枚举实际内容边界。大精灵、超格切片或越界对象不能据此保证完整取景。
- [PNG](../../src/map/map_export.gd#L140) 始终绘制实例色标、碰撞块、出生点；一致档只实现指定显隐/混合和排序段的近似，不是画布截屏。对象标记位置也不能替代完整资产的锚点与变换。
- 方案：保留“布局示意”快速路径；把现有一致档改名“按图层状态生成示意图”，准确列它的支持项。若要真实输出，复用同一渲染提取器和画面参数做离屏渲染，统一贴图、混合、层变换、Y 排序和实际边界，调试叠层另设选项。验收用同地图像素夹具覆盖上溢瓦片、缩放、遮挡、半透明、poly/path 和临时显隐。

### P2-05　声明校验、内容校验和写入能力不对称

[清单校验](../../src/project/manifest_validation.gd#L100) 查结构和部分 ID/码冲突；[递归行校验](../../src/project/manifest_validation.gd#L633) 主要查子字段 ID、kind/type 和层数。它不等于递归校验实际内容值、默认值、引用作用域、输入单位、跨字段约束。[ContentStore](../../src/content/content_store.gd#L149) 验读的是文件壳而非声明数据；[全项目内容字段引用检查](../../src/project/project_audit.gd#L235) 主要查顶层内容引用，不等同于所有域、类型和嵌套的审计。地图摆放物的 [transform 校验](../../src/map/map_data_validation.gd#L193) 只查对象壳，绘制、命中却会用内部比例和变换。身份码约定也不等于每处校验都实施合法字符、长度。

建议先定义一份可递归编译的字段 schema：明确缺省/空值、输入与存储类型、ID/码命名空间、数值有限性、范围、路径、哪类对象可引用及哪些检查阻断写入。优化前优先补“读入时可以保留的旧形态、编辑时允许的值、发布时必须通过的约束”三层，避免新校验吞扩展键。文件系统路径统一由项目适配器解析，读资源限定在预期根目录；试玩执行配置作为显式可信项目动作，结构化参数优先。

### P2-06　跨图配对的画布选点可能写入本图目标

[功能表单](../../src/ui/content_form.gd#L273) 和 [步骤表单](../../src/ui/steps_panel.gd#L855) 将配对值放进下拉的 `_mapKey`，但启动画布点选（[功能](../../src/ui/content_form.gd#L326)、[步骤](../../src/ui/steps_panel.gd#L895)）仍进入当前画布，回调检查“配对值有没有变”，不检查“候选是否来自该图”。普通实体引用只存实例码，一旦两图恰好同码还可能静默指到错误实例。

修复先禁止目标不在当前画布时启用点选，说明可用下拉；后续可以在只读目标视图上点选，返回完整 `EntityKey`/`EdgeKey` 或同类对象后由字段 codec 写回。覆盖实体、cell、edge 和步骤，不在四个 UI 入口分别补判断。

### P2-07　内容地图范围、默认值与状态反馈仍有多个漏洞

- [批量关系统计](../../src/project/project_audit.gd#L1030) 把本图正式及活体绑定相加，未按实例身份去重；内容入边扫描主要按目标 CID 命中，缺少同一条正式引用检查所用的目标功能过滤和递归覆盖。结果可重复计数或串到不同功能的同 ID。与 P1-02 共用索引后解决。
- [viewport_ref 控件](../../src/ui/field_widgets.gd#L665) 把无条件发送当前对象的 `emit` 注册为 commit，且回调没有把写失败的 bool 返给 [commit_fields](../../src/ui/content_editor.gd#L351)。未修改的空字段也会执行写回，可触发 [_ensure_content](../../src/ui/content_form.gd#L628) 并新建暂存绑定；写入失败又可能被当成成功继续切换。应复用标准变更检测与失败传播，并检查矩形的 `x+w/y+h` 是否允许超画幅；明确“未设”与“使用默认满幅”。
- [载图补发](../../src/canvas/editor_canvas.gd#L270) 和 [实例补码](../../src/core/undo_history.gd#L541) 都可能改变身份，但 [载图脏状态](../../src/canvas/editor_canvas.gd#L470) 只由 keep_dirty 与挂载补齐决定。旧图缺码可在本次会话有新码、干净保存却不写，下次重开重新发。把持久化迁移结果单独返回并纳入脏状态；明确“冻结继承投影”是持久迁移还是编辑会话状态。
- [格边取线段](../../src/canvas/editor_canvas.gd#L1019) 有一条在无条件 return 后的不可达代码；清掉遗留兜底，并由边规则定义退化行为。校验/候选/点选不能靠隐含线段等价。

## 4. 能制作哪些 2D 内容，哪些只能由游戏侧绕过

判定假设：游戏工程已提供可执行的模块、素材、加载器和声明。编辑器必须允许内容作者建立数据、连接关系、检查结果、重复操作并在游戏侧验收；用预制对象承载规则是正常分工。每项都可以由游戏代码强行解释，只有修改程序或 JSON 才能制作的部分不算编辑能力。

| 例子 | 现有契约能承担的部分 | 做不完的具体工作与通用补充 |
|---|---|---|
| 横版平台、箱庭银河城、俯视 RPG、射击、普通塔防 | 地形、贴图、实体、斜坡/单向等标记、地图跳转引用、触发/对话/波次参数、路径点、演出 | 多出生点可用实体表示，现成运行时策略可用功能表示。若需要自由碰撞、重叠高度或不同空间的边界，缺多边形/复合几何的专门校验、可见层归属和发布预览。优先开放通用几何工具，保留现有网格碰撞。 |
| 等距 ARPG、斜投影经营、多楼层战术 | 基线投影、斜基、层 offset/scale、排序段、锚点、实体 Y 排序 | 单根格空间、单套编辑相机；可用层或多个地图绕过，但不能原生换活动坐标、表达多层通行关系，斜基/三角层没有逐格 Y 交错。需要可选空间通道/局部坐标与排序字段，额外高度由游戏侧解释；共同投影与诊断应提供参照。 |
| 六边/三角战棋、拼图、方格异形板 | 可编辑规则格地图；有限格图可作为外部输入，下拉/画布拾取 cell id | 编辑器不能画、拆、合任意格、编辑邻接/门槛、维护任意边和格属性；规则边依赖瓦片导出与当前判据。增加通用拓扑文档（稳定 cell/edge ID、邻接、几何、属性），支持绘制、验证、批量和引用影响预览。先修 P1-03、P1-04。 |
| 节点地图、地铁/电路/工厂网络、对话状态图 | 可用实例与 port_ref；内容关系图可改接声明的内容字段。行为与流量留给游戏模块。 | 端口没有画布建立、选端、可视连线或运行时预览；内容关系图不是任意节点/边/条件/端口图。增加声明驱动的拓扑数据源与节点边编辑器，端口位置、类型和连接限制由 schema 提供。避免给每种游戏重写关系图。 |
| 解谜机关、分支叙事、任务链、卡牌/经营/全局数据 | 功能、可共享内容、结构化行、条件参数和关系图可以表达许多数据；由游戏实现推进或规则。 | 内容工作台从本图实例出发。缺少脱离假实例的独立命名数据集、全局关系、批量校验；条件依赖列表固定在清单，作者不能配置多组条件、分支或一实例多份同模块绑定。建议可选独立 ContentCollection/Graph 文档，实例与文档引用同一 ContentKey，开放声明的条件组合和可重复绑定，先保留现有单行策略作为默认。 |
| 竖屏、分屏、本地多人、房间热点、伪 3D / 轨道射击 | `viewports` 可存归一化点/矩形；正交等网格可放锚点；游戏侧能按这些参数渲染。 | 不能编辑并同时看多个参考画幅、图像热点、随相机变化的坐标或深度落点；`views` 无消费。先实现声明指定的静态画幅/参考图画布并支持目标拾取；动态/透视依赖可选游戏侧预览适配器，没映射时保持只读。 |
| 节奏、音乐关卡、技能帧表、镜头演出、弹幕 | 时间轴编辑步骤、轨道、时长、帧/拍刻度；支持图像帧参考与试玩。 | 缺音频/波形/播放同步、随时间变化的预览反馈和关键帧曲线；通用步骤可以生成结果，作者不能在编辑器直接对齐、逐帧核查。优先建立只读时钟、音频参考及跳转协议；曲线、事件轨/取样由声明逐步扩展。 |
| 开放世界、流式地图、程序生成、无界绘图 | 有限地图组、整图复制、自检、预设与统计；种子和生成参数可由内容承载。 | 没有稳定跨图世界布局的可视编辑、按块加载或生成结果可局部改写。若产品目标包含大世界，再加可分片地图/世界文档及生成缓存，不必在常规地图重构前实现。 |
| 纯菜单/视觉小说、全 UI 的策略、点选图文 | 可以用实体、内容、步骤和引用模型交付原型。 | 没有屏幕空间布局、响应式锚点、文本溢出及本地化预览；如果要求“全 2D 内容开发”，应通过独立布局文档或外部编辑器适配支持。若产品定义只含关卡，则在公开边界中明确 UI、素材生产和程序开发各自归属。 |

最低可用的通用扩展层宜只有三项：

1. **可注册的文档/空间**：地图、自由几何、格图、节点图、参考画幅、内容集合共用身份、撤销、引用和发布，编辑器内的核心几何与序列类型有限。游戏声明只是选择类型、提供字段、约束和资源。现有 v7 仍可读取，扩展键先作为并行文档或有版本的可选子文档验证需求。
2. **递归内容和引用 schema**：声明可描述独立数据、字段类型/单位、可重复绑定、引用目标域、可选连接限制。声明模式固定即可获得创建/校验/差量/复制。任意运行时代码、AI、物理、事件解释仍归游戏。
3. **显式的预览能力协商**：可选版本化接口，让独立运行的项目接收只读快照、地图/对象/时间/画幅身份并返回图像、标记或诊断。编辑器默认仍可以静态编辑，无适配器时说清观察边界。项目代码只在用户明确启动的独立进程内运行。

对应产品验收用三套小型接入项目：横版（门/斜坡/可复用房间）、格战棋（斜基与非规则邻接、地图和端口引用）、竖屏节奏/叙事（独立内容、参考画幅、时间对齐）。只实现游戏规则和资产一次，作者用编辑器独立制作第二份关卡/内容，保存、关掉再打开、试玩一致；需要手改 JSON 的步骤就是下一项产品缺口。生成、超大世界、全 UI 另建目标级别，不要求为通过单个接入样例过早做成万能 DSL。

## 5. 全局架构与性能

| 部分 | 判断 | 具体改法与衡量 |
|---|---|---|
| 清单、资产、功能池（`assets/`、`content/*_decl`、project） | 声明域和 ID/码分离是正确的。扫描和手写共存、保留停用条目也合理。池缓存每次查仍要算结构散列；不同域重复解析/补码，静态归一化可能被可变字典和运行态键牵动。 | 每次清单接入/修改编译一个不可变 `ProjectSchema`，由清单 revision 发布，预建资产、功能、字段、时机反查。明确保留码、缺失资产、禁用资产和运行时只读模型；按文件内容变动增量重链，纹理缓存按字节预算和指纹失效。 |
| 文档与持久化（`map/`、`project/document_*`、`content_store`） | 摘要复验、快照和逐目标收据是正确的。普通/冻结执行实际有分叉，map/manifest 内容的解析和写入还散在 UI。JSON 差异可看、易集成，应保留；编辑中无须反复恢复整图 JSON。 | 单一命令/计划执行器、统一文件仓储适配、运行前锁定目标与目标版本，复用历史、写前校验与收据。显式接入外部变化，保留扩展字段；改用固定顺序输出，避免遍历顺序制造版本噪声。 |
| 画布与输入（`editor_canvas`、`layer_ops`、`canvas_input`、`selection_ops`、`region_ops`） | 控制器分文件降低了浏览成本，仍有宿主反向引用、私有状态被访问、薄桥接很多；这解释了为何 UI 读活体、下拉读快照、审计读盘三路长出来。场景节点兼作数据模型让几何批改、撤销和重建都被节点生命周期绑住。 | 先抽 `MapDocument` 和瓦片/实体读视图，以 command 返回 patch；已有 TileMapLayer 继续当瓦片渲染及投影层。先迁移格边读查询和区域计划，用实际收益验证边界，再逐步从 `app/cvs` 改为窄接口，避免一次搬完。 |
| 预览与导出（`grid_space`、`map_view_data`、`tri_tile_view`、`content_preview`、`map_export`） | 格空间的纯几何和自绘分块应保留。[预览](../../src/ui/content_preview.gd#L323) 虽缓存瓦片清单，每次重绘仍走全层；[导出](../../src/map/map_export.gd#L53) 有规模预算，是 CPU 上界保护，并不保证交互线程无停顿。实际包围盒与呈现规则复用不足。 | 抽取 `RenderSnapshot`：每层变换预编译、按空间块查可见瓦片、实体包围盒/远距简化可共享；PNG 大批次考虑后台纯像素工作与取消，主线程只负责对象/纹理交接。设置图片解码前尺寸预算。 |
| 撤销（`core/undo_history`） | 笔画和实例差量、内容写前摘要是对的。层、区域和批量操作走整图快照合理但受最大字节数约束不足：80 步只限数量，`extract()` 深复制基础文档再抄一遍动态数据。重建期由一帧等待与 guard 管理，很难验证每路径。 | 先记录单步/累计字节和最大成本；区域、裁剪、层管理用稀疏 patch；只对格式迁移保留整图快照。将撤销内容数据从磁盘即时写入策略拆开，明确“撤销”和“提交”的粒度。 |
| 索引、审计和复制（`reference_index`、`project_audit`、`clone_plan`、`rel_graph`） | 稳定键、冲突计划和读不完整即停止是好选择；同样的引用概念多遍历，浏览索引即使命中也做清单散列/地图目录签名，破坏性操作会反复扫描。 | 一个递归引用遍历器，缓存按“文档内容版 + schema 版 + 活体增量”更新，查询统一支持快速视图/强一致重核两个模式。复制规划读不可变索引，写入只消费计划。名称、ID 和引用解析统一，保留坏文件诊断。 |
| 内容、表单、步骤与外壳（`ui/`） | 工厂控件、已存在的值检查和模式共享值得继续用。1,694 行的表单兼管 UI、写盘、内容库、批量、图；步骤用展示数组和局部序号处理身份，字段事件有多个刷新/提交入口。时间轴已有轨道命中索引，但绘制仍逐步骤循环。 | 以业务 slice 拆为 FormState/ContentLibrary/TimelineModel，UI 只传稳定选择键和命令；步骤日后需要可持久化身份时加版本键。控件统一返回“未改/已应用/冲突”，异步窗口统一用操作令牌。按可见轨道与时间窗口索引，虚拟化长实例列表和步骤列表。 |
| 试玩、诊断、工具性（`playtest`、`issues_drawer` 等） | 结构化 argv 与有界日志读取合理；已有地图摘要验收。试玩仍只给终点证据，没有机器可读加载/模块诊断；教程容易把程序存活误作内容有效。 | 结构化试玩握手报告 map/schema revision、加载缺失和错误定位；为视图、日志及进程生命周期给明确支持边界。项目默认入口用显式投影/出生点规则，测试场景的结果能跳回相应字段。 |

先观察再优化。统一采样三档：小图（1 万瓦片 / 200 实例）、常规大图（10 万 / 2,000）、压力场景（100 万稀疏瓦片 / 1 万实例，及时间轴 5,000 步）。Windows 目标机记录相机/笔刷帧耗时 P95、首次开图、热缓存查询、切换内容列表、保存与导出、撤销峰值字节、跨图引用审计。以当前版数据定目标；交互可先采用 60 Hz 模式下 P95 约 16.7 ms 的帧预算，再按硬件测得的热点调整。只读/后台不是默认正确：主线程资源访问、文件摘要和进程取消应单独测量。

## 6. 实施顺序与合并标准

1. **稳数据**：先修 P1-01、P1-02、P1-05，共用复合键与提交规划；补释放忙状态、异常路径和恢复的可观察回执。先写清持久化行为，再更新两份规范。
2. **稳几何**：落实 P1-03、P1-04、P2-03、P2-06；共用网格和边规则。对渲染明确“示意”及“一致”的承诺，修复可实测的材料/坐标差异。
3. **做通用创作扩展**：用三组样例验证独立内容、拓扑和画幅三条架构接缝，再扩时间预览、开放世界或 UI 文档。关键决定是哪些数据作者在编辑器内拥有，哪些只由游戏代码提供。
4. **只对测得的热点优化**：先修多次全量扫描、重复解析与快照高峰；对架构改动保留当前 v7 读写对照夹具、未知扩展字段往返及失败注入。规范示例应来自同一套可验证夹具，避免再出现静态示例与生产路径分歧。

每阶段最多增加需要的能力；当前仓库最有价值的部分是游戏与编辑器之间的数据契约，下一步是让几何、引用和提交各有唯一的工作数据源。
