# 游戏侧开发规范

本文给负责**游戏工程**的 AI。目标是把一套可运行、可配置的游戏能力交给作者，让作者用 BIRD 编辑关卡、规则、流程、演出和游戏界面。先按下面的接入步骤做一条能从编辑器走到游戏的链路；字段、坐标、文件及进程协议见[游戏侧数据协议参考](GAME_SIDE_PROTOCOL.md)。

## 先明确分工

- **游戏工程提供**素材、实体、玩法规则、输入与物理、运行时相机、UI 控件及行为，并用 `editor/editor_manifest.json` 声明作者可以修改的参数、可使用的模块和可接线的出口。游戏读取编辑器发布的数据并执行。
- **编辑器提供**通用的地图摆放、图层、表单、资源及引用选择、流程连线、时间轴和 UI 布局。编辑器读取声明生成编辑入口，不执行清单里的游戏逻辑，也不生成、修改游戏脚本。
- **固定大类，按项目声明具体模块。** 编辑器认识 `assets`、`functions`、`conditions`、`steps`、`triggers`、`screenModules` 等声明位置，以及数字、布尔、文本、数组、记录、曲线、引用等字段形态。项目自行声明卡牌、技能、载具、设置面板等模块的 ID、字段及候选。用已有形态组合时无需为玩法加编辑器代码。新增一种通用数据类型或专用编辑交互才需要扩展编辑器。
- 编辑器在打开项目时加载清单并扫描约定的资产目录。外部改了清单或素材后，先发布或保留当前编辑，再重新打开项目查看结果。运行时模块由游戏注册和实例化；清单声明不会自动装载游戏脚本，也不用以游戏类型作为编辑器分支。

## 接入步骤

1. **列出作者要改什么。** 先区分游戏规则、制作参数和玩家状态。把频繁变化的创作决策做成具名字段或流程出口，例如伤害、卡牌池、分支条件、返回屏幕和结算内容。状态机、碰撞响应、存档、声音混音等由游戏实现，再暴露作者需要调的部分。
2. **建立清单和游戏入口。** 在工程根创建 `editor/editor_manifest.json`。无地图游戏也能接入；按需声明 `startup`，由作者选择已保存的内容、屏幕、地图或入场端口。启用试玩时配置 `playtest.executable` 和逐项的 `args`；游戏要能不依赖编辑器独立运行。完成条件：打开项目能看到声明的内容类型或模块，运行时能识别其稳定 ID。
3. **实现数据加载。** 读取实际发布的清单、`maps/*.json` 和 `<contentDir>/<功能声明 ID>/<内容 ID>.json`（`contentDir` 默认为 `content`）。按下节建立查找表。正常启动使用 `startup.target` 或游戏缺省入口；接入试玩后优先处理本次显式入口。完成条件：游戏读取作者刚发布的文件，修改字段后重新启动，结果随之改变。
4. **在编辑器里做第一条回路。** 使用编辑界面建内容、设参数和连线，保存并重开项目，确认值、顺序、引用都还在。独立运行从入口走到一个可验证的结果；同时测一条失败、取消或未接线的分支，按游戏模块定义处理。不要用手写地图或内容替代编辑器往返验证。
5. **按需扩展能力。** 只读下方对应章节。要看到真正的着色、字体、动画、遮挡或相机效果，接入游戏渲染预览或试玩。发布时用实际要交付的游戏运行方式再走一次入口。

## 选择声明及储存位置

| 作者要配置的内容 | 游戏侧声明位置 | 编辑完成后从哪里读取 |
|---|---|---|
| 图集、背景图片、实体预制件 | `assets[]`，用 `kind` 区分 `scene` / `entity`；场景资产用 `shape` 细分 | 根据地图中的资产 ID 查清单；瓦片在 `tiles`，摆放图片与实体在 `objects` |
| 某一个实体的位置、局部参数、引用 | 资产自己的 `fields`、`ports`；必要时声明 `visual`、`anchor` | 地图 `objects[]`；声明的实例参数在 `props`，键是字段 `id` |
| 可重用的规则、对话、技能、题目、卡组、任务 | `functions` 与对应的 `fields`；实体自带功能用 `assets[].functions` 引用功能 ID | 独立内容或实例绑定所指的内容文件；`function` 和 `fields` 使用执行码 |
| 条件、事件时机、音频、按时间执行的演出 | `conditions`、`triggers`、`audio`、`steps`；功能启用演出用 `steps: true` | 实例绑定、内容字段和内容 `steps`。游戏决定触发、条件求值、音频播放、时间与分支执行 |
| 地图专属规则或流程出口 | `mapContentSlots`、`mapOutputs` | 地图 `meta.contentSlots`、`meta.flowOutputs` |
| 多张地图共享的绘制、碰撞及事件 | 绘制和碰撞沿用地图格式；需要接事件时在 `triggers` 中声明 `eventTargets` | 作者保存的 `eventLayers` 以及可选的 `drawingMap` 对应文档 |
| 标题、设置、背包、HUD、结算或其他游戏内界面 | `viewports` 和按需使用的 `screenModules` | 清单 `views[].layout`；模块参数 `props` 用字段 `id`，连线在 `outputs` |
| 程序生成的地图和连续世界 | `mapGenerators`、生成能力 `generateMap`；作者编辑 `worldLayout` | 已发布地图、清单中的分块绑定；随机逻辑、流式挂载和替换策略由游戏运行时执行 |

普通参数用 `kind: "input"` 和已有 `type`；枚举或资源选择用 `kind: "choice"`，静态用 `options`、动态用协议允许的 `source`。用 `array` / `record` 表达有序卡组、规则行、波次、路线和分支，按保存顺序读取。需要编辑器识别、定位、校验、重映射的引用，声明对应的引用类型或动态来源；不要把实际引用伪装成普通文本。把单位写进字段显示名。用 `default` 明确缺键语义；显式的 `0`、`false`、空列表或清空的目标不能被误当成未填写。

## ID 与读取规则

启动时从**磁盘清单**建立索引。声明 ID 是稳定键，显示名可改；执行码也是稳定键，两者不能互换。

| 读取位置 | 解析规则 |
|---|---|
| `maps/*.json` | 由 `meta.code → 地图文件` 建索引。实例按 `(地图码, objects[].code)` 定位；不能用实例码查全项目，也不能拿地图文件名当地图码 |
| `objects[].asset` | 查 `assets[].id`。实体类型另有 `assets[].code`；它与实例码不同 |
| `objects[].functions[]` | 由 `fn` 执行码反查功能声明 ID，再用 `content` 完整 ID 找内容文件。逐条处理，支持 `repeatable`，遵循 `enabled`、时机和游戏的顺序约定 |
| 内容和演出步骤 | 内容路径用**功能声明 ID**作目录，文件内 `function` 用**功能执行码**；`fields` 按该作用域的字段码读取，`steps[].step` 用步骤执行码 |
| 实例与屏幕模块参数 | `props` 使用对应声明字段的 `id`；按模块确认默认值、字段含义及用途 |
| 流程目标 | 内容为 `{function, content}`（功能声明 ID、完整内容 ID），屏幕为 `{view}`，地图为 `{map}`，入场端口为 `{map, inst, port}`。使用目标域和声明的地图上下文，不从字符串猜目标 |

新实例内容可使用「地图码—实体类型码—实例码—功能码—内容码」；项目内容也可用 `project-…`。把两者都作为**完整不透明键**读取，内容身份按 `(功能声明 ID, 内容 ID)` 解析。不要由内容 ID 的前缀推断当前调用实例、地图或所属权；内容可以被复用，地图上下文应随绑定或目标显式传入。

缺失的声明码可以由编辑器补发；先保存清单再让游戏读取相应产物。不要在游戏里自己补发、重写或把随机生成的码硬编码进玩法。游戏可用稳定声明 ID 注册处理器，再从当前清单映射到码。改显示名可以直接做；修改已发布的声明 ID、字段码或目标形态时，要有对应的数据迁移。普通游戏进程只读发布的创作文件；玩家设置、存档和进度另存。预览快照、生成结果和试玩回执只写入协议约定的位置。

## 按功能接入

### 地图、视角和场景变化

- 用同一数据契约实现正交俯视或侧视、等距、六边、三角或自定义双基。网格投影、拓扑、图层独立格系、锚点、自由摆放、碰撞和运行时相机是不同的概念。先按[地图格式与坐标](GAME_SIDE_PROTOCOL.md#map-data)确定存储坐标，再由游戏选择画法、移动和实体行为。
- 保留图层稳定 ID 与顺序；读取初始可见性、偏移、缩放和 `parallax`。默认 `1` 正常随镜头滚动，`0.5` 半速，`0` 屏幕中固定。编辑器中预览这些参数，实际镜头移动时由游戏应用。
- 场景局部变化也是游戏能力。需要换某张图的素材、切换指定图层或显示一组对象时，游戏实现模块并声明作用对象、范围和新状态。作者选图层/实体/坐标和目标值，游戏通过该模块修改运行时场景。不要回写编辑器地图来实现游戏事件。

### 图组事件层

1. 游戏在 `triggers` 定义什么时候发事件，例如 `round_finished`，并以 `eventTargets` 声明可接到的内容类型、屏幕、地图或入场端口。
2. 作者选择该层适用的地图、接事件目标，按需使用「保存并编辑绘制层」。省略 `maps` 表示无范围限制，`maps: []` 表示没有地图命中。
3. 游戏按**当前基础地图码**选择全部匹配图组，再按**时机执行码**查 `events`。每个 `drawingMap` 是一份独立的地图文档，按普通地图格式读它自己的图层、瓦片、摆放物和碰撞；保留文档和实例身份，按各文档的格空间解析坐标，不递归匹配图组。游戏决定何时显示、启用碰撞、执行事件，以及多组命中时的顺序。
4. 验收至少测两个入口：一个命中并加载相应绘制、碰撞和事件目标，另一个不命中。希望无地图的游戏共享某个事件时，由游戏显式消费无范围限制的层。详见[图组事件、正式入口及试玩协议](GAME_SIDE_PROTOCOL.md#entry-events-playtest)。

### 游戏界面和设置

1. 简单面板、文本和按钮可以直接排版。需要滑杆、按键绑定、物品列表、选项卡等实际控件时，游戏实现组件，在 `screenModules` 用模块 ID 声明作者要改的字段和出口，例如 `player-options` 的默认音量、默认字幕和 `accepted`。
2. 作者在参考视图选模块，配置尺寸、锚点、画幅变体、文字及参数，接好 Apply、返回或取消。游戏按实际尺寸、所选画幅 ID、布局父子关系与层序建 UI；用 `props` 和声明默认值初始化组件。布局里的 `style` 由游戏解释。
3. 处理玩家实际操作：例如音量滑杆改混音、字幕开关影响字幕、Apply 写玩家配置再触发相应出口。重启从玩家配置读值，未设置时才回落到作者的默认配置。修改键位、分辨率、安全区、手柄焦点等同理，由游戏按自己的平台及 UI 框架实现。
4. 验收时让作者在编辑器里保存初值及出口，游戏中确认初值、操作结果和导航；需要持久化的项目再验证重启。若用游戏渲染预览，按[屏幕布局、模块和预览协议](GAME_SIDE_PROTOCOL.md#manifest)接入，渲染请求里的当前布局与画幅。

### 玩法、流程、音频和演出

- 用同一功能声明建多条内容。卡组可以是带数量的记录数组，节奏事件可以是时间轴步骤，运输网络可以是地图实例和具名端口。条件的求值、同一时机的处理顺序和分支缺省由游戏定义。
- 需要作者编排触发、时序或状态转换时，使用已声明的时机、步骤、曲线与流程目标。使用 `contentMapContext` / `viewMapContext` 及配对字段声明调用需要的地图上下文；**流程连线保存目的地，不替游戏执行跳转**。
- 截取真正的演出画面时，用预览请求里的时间、内容、地图快照与画幅渲染；正式播放仍由游戏运行。音频、动画、计时和取消的处理应共用同一套游戏逻辑。

## 最小接入例：可编辑的游戏启动内容

下面是一个不需要地图、图集或预制件的清单。创建后在编辑器中新增 `intro` 内容、设置标题并保存，再在「启动入口」选择该内容。示例未固定执行码；公开内容之前先保存由编辑器补码后的清单。

```json
{
  "version": 1,
  "projectName": "Signal",
  "functions": {
    "intro": {
      "name": "开场",
      "fields": [
        {"id": "title", "name": "标题", "kind": "input", "type": "string", "default": "信号已收到"}
      ]
    }
  },
  "startup": {"contentTypes": ["intro"]}
}
```

游戏注册 `intro` 处理器。运行时读 `startup.target`，按其 `function` 和 `content` 找文件；用 `functions.intro.code` 核对文件的 `function`，以标题字段声明中的 `code` 读取 `fields`，缺键时用声明的 `default`。将结果显示在真实游戏界面。改变标题、发布、重开编辑器，再启动游戏确认新标题。需要启动 Godot 试玩时，给 `playtest` 配置本机 Godot 可执行文件、`projectEntry: true` 和参数数组 `["--path", "%projectpath%", "--", "--map=%mapfile%"]`；此例项目启动收到空的 `--map=`。

## 交付给作者前

- 清单可载入，作者需要用的每项能力都出现了。至少实际在编辑器里创建、保存并重开一条代表内容，检查数据和引用往返。
- 游戏能用清单和发布文件独立执行这条内容。更换其中一个关键参数或目标，结果随之变化。若使用地图、演出或游戏 UI，再各走一次实际入口，覆盖项目采用的坐标、输入、画幅或持久化行为。
- 交付游戏侧的模块/处理器、清单声明、依赖资产及运行方式。可以复用[独立设置与屏幕测试](../tests/screen_game/game.gd)、[卡牌规则测试](../tests/card_game/game.gd)、[运输网络测试](../tests/network_game/)中的数据读取方式；按本工程实际需要接入。完整字段形态以[协议参考](GAME_SIDE_PROTOCOL.md)为准，编辑器操作见[功能说明](EDITOR_FEATURES.md)。
