# 初版代码审查 · 任务三：能否承担「所有 2D 游戏（各种类型、各种视角）」的开发

> **评判基准（用户给定，本文全程遵守）**：编辑器**不为任何特定游戏类型做**，采取「游戏工程侧 / 编辑器侧分离」——游戏工程侧提供**可组装、可编辑的成品模块**并暴露接口，编辑器侧实现**真正的拼装**。
> 因此本文的判断标准不是「编辑器有没有内置塔防/战棋功能」（内置才是设计失败），而是：
> **① 游戏侧能不能用现有接口把这类游戏的模块与数据表达出来；② 编辑器侧有没有足够的通用原语把这些模块拼起来；③ 缺失的能力属于游戏侧职责还是编辑器侧职责。**
> 事实来源：`src/**/*.gd` 实际代码。文档自认的边界（`EDITOR_FEATURES.md:709-731`）已纳入，但**不采信注释作为能力存在的证据**。

## 0. 结论先行

**目前达不到「所有 2D 游戏、各种类型和视角」的目标，但瓶颈的位置和直觉相反：不在游戏侧，在编辑器侧。**

| 维度 | 判定 | 说明 |
|---|---|---|
| **玩法 / 内容 / 规则**（游戏类型维度） | [OK] **覆盖面很广，架构方向正确** | 功能、条件、步骤、音频、时机、字段全部由清单声明、游戏侧实现；编辑器只做绑定与填值。理论上任何玩法的**行为**都能外置，编辑器不需要懂「塔防」或「视觉小说」 |
| **空间 / 视角**（坐标与几何） | [NG] **只覆盖 1.5 套投影，且被单一正方形格锁死** | `grid_space.gd` 只有 orthogonal / isometric；`manifest_validation.gd:433` 把 `gridProjection` **枚举锁死**为这两个值；`editor_canvas.gd:216` 用 `Vector2i(tile_px, tile_px)` 强制正方形格。六边形、斜 45° 带高度、自由旋转、非网格连续空间、非正方形格全部做不了 |
| **组装关系**（"真正的拼装"） | [NG] **只能摆单个对象 + 填字段 + 绑功能** | `objects[]` 是**扁平列表**，没有父子/嵌套、组合实例、连线、路径、区域、节点图。游戏侧能交付 prefab，但编辑器只把它当一个点摆下去，不能展开、不能整体带子件移动 |
| **多图 / 世界结构** | [~] **只有独立地图文件 + 单值跨图引用** | 没有世界坐标、图间邻接拓扑、分块（chunk）、关卡分组/继承 |
| **表现与调试闭环** | [~] **静态贴图/矩形预览 + 单向外部试玩** | 无骨骼/粒子/动画预览扩展点、无 autotile、无试玩双向数据通道；层参数与 transform 的**数据结构已有但缺编辑控件** |

**一句话**：分离架构成功地把「玩法」解放了，却把「空间」和「组装」固化成了一种特定形态 —— 一个隐含假设：**关卡 = 单一正方形网格上的瓦片 + 扁平对象列表 + 整格碰撞 + 线性时间轴**。任何不符合这个假设的 2D 游戏，游戏侧无论补多少模块都补不上，因为坐标映射、命中测试、框选、吸附、格线、视图变换、拼装控件全部属于编辑器职责，无法下放（下放等于每个游戏重写一个编辑器，恰好推翻分离初衷）。

## 1. 先厘清职责边界：什么该游戏侧补，什么必须编辑器侧补

这是整个分析的钥匙。判断依据：**这个能力是否需要编辑器「理解数据的结构」才能提供编辑交互？**

| 层 | 职责 | 现有实现 | 是否可以「游戏侧自己补」 |
|---|---|---|---|
| **L1 玩法行为层** | 战斗、AI、经济、对话执行、胜负判定、波次逻辑… | `functions`/`conditions`/`steps`/`audio`/`triggers` 由清单声明，编辑器只存绑定与字段（`fn_bind.gd`、`content_form.gd`、`field_widgets.gd`） | [OK] **可以，且应该**。这是分离架构设计好的地方，编辑器无需改动 |
| **L2 可编辑接口层** | 游戏侧暴露哪些字段、什么类型、选项从哪来 | `kind: input/choice` + 9 种 `INPUT_TYPES` + 动态 `source`（`manifest_validation.gd:17`、`content_form.gd:214-289`） | [OK] **基本可以**。字段类型不够时可加通用类型（见 R-06），但不需要类型专属面板 |
| **L3 空间/坐标层** | 格↔像素、投影、格线绘制、命中测试、框选、吸附、视图变换 | `grid_space.gd`（两套固定线性变换）、`tileset_cache.gd:39-40`（只设 `TILE_SHAPE_ISOMETRIC`）、`editor_canvas.gd:216`、`canvas_input.gd` | [NG] **不能**。全部在编辑器画布内核里，`gridProjection` 还是枚举校验锁死的。游戏侧改不了画布 |
| **L4 组装关系层** | 父子嵌套、组合实例、连线、路径、区域、引用可视化 | `objects[]` 扁平（`map_data_validation.gd:126-172`），只有 `props` 里的字符串引用 + `functions[]` 绑定 | [NG] **不能**。需要编辑器提供通用数据段与编辑控件；让游戏侧把路径塞进 `props` 数组等于把编辑器退化成 JSON 文本编辑器 |
| **L5 表现与预览层** | 实体在画布上长什么样、动画/粒子/骨骼 | `entity_node.gd`（Sprite2D + 矩形/贴图 + `data_transform`）、`asset_decl.gd` 的 `prefab`/`visual` | [~] **部分**。游戏侧可用 `visual` 声明，但没有「呈现插件」扩展点，复杂表现做不了预览 |
| **L6 运行/调试闭环** | 试玩、状态回传、参数热调 | `playtest.gd` 单向 `OS.create_process`（还只支持 Windows） | [~] **部分**。需要编辑器定义双向协议 |

> **关键推论**：用户目标里「各种类型」主要落在 L1/L2，**已经基本达成**；「各种视角」和「真正的拼装」落在 L3/L4，**这两层是编辑器自己的活，游戏侧代劳不了**。所以「能不能做所有 2D 游戏」的答案，取决于编辑器愿不愿意把 L3/L4 从「写死」改成「可插拔」。

## 2. 现有能力盘点（先肯定已经做对的部分）

在指出缺口前，必须承认初版把分离架构里最难的部分做出来了，这些是后续扩展的地基：

1. **玩法完全外置**：`GAME_SIDE_STANDARD.md` 的契约 + `manifest.gd` 的声明加载 + `fn_bind.gd`/`content_form.gd` 的绑定与字段编辑，使编辑器**不硬编码任何游戏内容**（`EDITOR_FEATURES.md:86-87` 的「清单驱动」经核对属实）。
2. **五段身份码与引用体系**：`content_id.gd` 的「地图-实体类型-实例-功能-内容」+ `map_store.gd:112-135` 的 `code_map` + `region_ops.gd:362-367` 的 `_remap_refs_in`，让跨实体/跨图引用有了**通用**表达，改名不破坏引用（`GAME_SIDE_STANDARD.md:548`）。这是"组装关系"的雏形 —— 只是目前只支持「字符串指向」，不支持结构关系。
3. **声明式可编辑接口**：`field_widgets.gd` 按 `kind` 渲染，未知声明只读展示（避免静默写坏数据）；`content_form.gd:214-289` 的 `source` 支持 `map` / `entity_inst:` / `entity_type` / `audio:` / `asset:` 动态选项。游戏侧可以声明相当丰富的参数。
4. **通用时序原语**：`steps` 的 `at/duration/track/blocking` + `step_timeline.gd` / `timeline_view.gd` 的冲突检测与拖块，能表达演出、波次、对话序列等"何时做什么"。
5. **混合层栈与遮挡模型**：`meta.layers` + 层内 Below/YSort/Above 三段容器（`editor_canvas.gd:254-295`），以及 `parallax`/`ySort`/`offset`/`scale`/`blend` 层参数预览（`:279-292`）—— 这套机制对横版/俯视的多层表现是够用的。
6. **试玩命令模板**：`playCommand` + `%mapfile%`/`%projectpath%` 变量替换，把运行入口交给游戏侧。

**这些能力合起来，已经能覆盖「正交网格 + 实体摆放 + 内容绑定」这一类游戏的绝大部分开发需求**（例如：横版平台、俯视 RPG、方格战棋、简化塔防、解谜、视觉小说的线性部分）。问题不在这一类做得不好，而在于这一类之外的空间形态被硬性排除了。

## 5. 根因归纳：编辑器侧缺失的 5 类通用原语

把上面的 [NG] 归并，本质是 5 个通用机制没做（**都是游戏类型无关的**）：

### A. 可插拔的坐标系 / 投影（最根本）
现状：`grid_space.gd` 两套固定变换 + `manifest_validation.gd:433` 枚举锁死 + `editor_canvas.gd:216` 正方形格。
缺的是一组**接口**：`to_px / to_grid / cell_polygon / neighbors / hit_test / bounds / draw_grid`。只要这层抽象出来，六边形、2:1 菱形、非正方形格、任意线性/仿射变换都能由游戏侧注册实现，编辑器只调用接口 —— **这恰恰是最符合分离思想的做法**，而现在的硬编码反而是违背了它。

### B. 通用几何数据段
现状：地图只有 `tiles`（格集合）、`collision`（格集合）、`objects`（点列表）。
缺的是与 `objects[]` **平级**的通用段：`paths[]`（点列/样条）、`regions[]`（多边形/圆/矩形）、`links[]`（对象间有向连线）。这些是纯几何、不属于任何游戏类型；配上同样的身份码与引用重映射，就能一次性支撑塔防路径、竞速赛道、战棋范围、物理解谜碰撞、对话节点图。

### C. 组合实例（「可组装的成品模块」的落点）
现状：`asset_decl.gd` 有 `prefab` 字段（`GAME_SIDE_STANDARD.md:180`），但编辑器只把它当**呈现引用**：`editor_canvas.gd:351-373` 把每个 `objects[]` 条目 `make_object()` 成一个独立 `EntityNode`，没有 `children[]` / `parent`，没有子件展开，没有整体带子件变换。
**这是「游戏侧提供可组装成品模块、编辑器侧真正拼装」最直接的落空**：游戏侧交付了一个由多个部件组成的 prefab，编辑器只能把它当一个点摆下去。

### D. 编辑控件与数据能力对齐
`entity_node.gd:58` 已支持 `data_transform = {scale, rotation, flip_h, flip_v}`，`meta.layers` 已支持 5 个层参数，`props` 里已有 `w/h` 与 `sortAnchor` —— **数据层全都有，只缺 UI 控件**。这类是投入最小、收益最直接的一批（R-04）。

### E. 试玩与校验的双向闭环
`playtest.gd` 是单向 `create_process`，无状态回传；`project_audit.gd` 是纯静态字典扫描。需要游戏侧参与的语义校验（「这个刷怪点是否可达」「这条路径是否闭合」）目前没有承载点 —— 而按分离思想，**这类规则应该由游戏侧声明、编辑器执行并汇总**，而不是编辑器内置各类型规则。

> **原则**：补充的全部是**通用机制**，不含任何游戏类型专属面板。R-01…R-05 是解锁「各种视角 / 真正拼装」的关键路径；R-06…R-11 是配套。
> 每条标注【编辑器侧】/【游戏侧】/【契约】，避免把编辑器该做的活推给游戏侧。

### 第二优先：工程与生态闭环

### 明确「不该做」的反模式

[NG] **不要在编辑器里内置「塔防波次面板」「战棋网格面板」「对话树面板」「谱面编辑器」**。这些是类型专属 UI，做进去就等于推翻「编辑器不为任何特定游戏类型做」的前提，也会让编辑器随游戏类型无限膨胀。

[OK] 正确路径是 R-01…R-06 的通用原语 + 游戏侧用「清单声明 + prefab + 字段控件 + 校验规则」**组合出**这些编辑体验。例如塔防：游戏侧声明一个 `path` 几何段 + 一个 `wave` 功能 + 波次字段，编辑器用通用路径控件和时间轴就能拼出来，不需要知道「塔防」是什么。

## 7. 优先级与验收标准

| 阶段 | 内容 | 验收标准（可测） |
|---|---|---|
| **阶段 0（前置）** | 修《AUDIT_CODE.md》C-01…C-07 的 P0 缺陷 | 实体复制粘贴可用；删层真的删 `objects[]`；瓦片变换 0..7 往返幂等；复制地图码唯一；`map_ref` 按码校验；playtest 校验生效；层操作 await 链完整 |
| **阶段 1** | R-04（补齐控件）+ R-01（GridProvider 接口，先实现 hexagonal 与矩形格） | 一个六边形项目 + 一个 2:1 矩形格项目能在编辑器里涂刷、框选、放实体、保存重开后位置一致；混投影有 warning |
| **阶段 2** | R-02（几何段）+ R-05（形状碰撞） | 一条样条路径、一个多边形区域、一个斜坡碰撞能被编辑、保存、重开无损；引用重映射在区域复制时仍成立 |
| **阶段 3** | R-03（组合实例）+ R-06（控件注册） | 游戏侧交付一个含 3 个子件的 prefab，编辑器能展开、单独覆写子件字段、整体拖动并正确落盘 |
| **阶段 4** | R-07…R-11 | 游戏侧自定义规则出现在问题抽屉；试玩可双向定位实体；世界视图能拼接多图；时间轴支持 BPM |

**每个阶段的通用验收底线**：新增能力必须是「类型无关」的 —— 用一个**不属于该能力目标类型**的示例项目也能跑通同一套机制，否则说明又不小心写成了类型专属逻辑。

## 8. 回答用户的三个子问题（收束）

**Q1：目前能不能承担所有 2D 游戏（各种类型、各种视角）的开发？**
不能。类型维度（玩法/内容/规则）因分离架构覆盖面已经很广；但视角维度只支持「正交正方形网格」和「半套等距涂刷」，组装维度只支持「摆单点 + 填字段 + 绑功能」。六边形、带高度的 2.5D、自由旋转、非网格连续空间、非正方形格，以及需要组合/路径/区域/节点图的类型，目前都做不了。

**Q2：具体是哪个部分做不了？**
不是「缺某个游戏模块」，而是编辑器侧的 5 类通用原语缺失（第 5 节 A–E）：可插拔坐标系、通用几何数据段、组合实例、已有数据的编辑控件、试玩双向闭环。根因是 `grid_space.gd` / `manifest_validation.gd:433` / `editor_canvas.gd:216,351-373` 把关卡形态写死成了「单一正方形网格 + 扁平对象列表」。**这部分属于编辑器职责，游戏侧补不了**（下放等于每个游戏重写画布，违背分离初衷）。

**Q3：应该怎么补充或修改？**
按第 6 节 R-01…R-11，**补通用机制、不补类型功能**：先把坐标/投影做成可插拔接口并放宽清单枚举校验，再加与 `objects[]` 平级的几何段、组合实例与呈现/控件/校验的扩展点；同时把数据层已有但 UI 缺失的控件补齐（最低成本）。所有扩展都通过「清单声明 + 游戏侧实现」接入，编辑器侧只提供调度、渲染与通用编辑交互。

## 9. 本任务的核验边界

- 能力判定基于 `src/**/*.gd` 静态阅读，**未运行 Godot**，因此「能/不能」指**当前代码路径是否提供该能力**，不含「游戏侧另外写一套运行时绕过编辑器」的情形（那不属于编辑器能力）。
- 「游戏侧可以补」的判断是**架构层面的职责划分**：只要编辑器提供声明接口，游戏侧即可实现；这不代表现成已有，需按 R-06/R-07/R-11 先补扩展点。
- `tests/`、`tools/`、`.tscn`、`project.godot` 不在用户限定的审查范围内，未据此推断能力；`editor.tscn` 只在检索中被扫到，未纳入分析。
- 类型矩阵是**能力覆盖评估**，不是逐类型实测；标注 [OK] 的类型也可能受《AUDIT_CODE.md》P0 缺陷影响（例如 C-01 令任何涉及复制粘贴的工作流都不可用）。
